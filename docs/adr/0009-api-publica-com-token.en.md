# ADR 0009 — The public API: the token identifies who, and the verdict is still a single one

## Status

**Proposed** — 2026-09-09.

Required by: [`AGENTS.md` §16](../../AGENTS.md) — *"changing public contracts"* is on the list of decisions that require an ADR, and opening the API is **establishing** a public contract, the strongest case of the rule.

Depends on: [ADR 0003](0003-organizacao-por-ontologias.md) — the routes call each ontological module's public API, never the `Repo`.

Realizes: [spec 061](../../specs/061-api-publica/spec.md). Unblocks: [spec 062](../../specs/062-servidor-mcp/spec.md) — the MCP server is a consumer of this API.

Grounded in: [security assessment of 2026-09-09](../seguranca/2026-09-09-api-com-token.md) — 18 findings, ten of high severity.

## Context

### The starting point, measured

`lib/the_band_web/router.ex:44-46` declares the `:api` pipeline and **no `scope` uses it**. There is no token module, no `Authorization`, no JSON controller besides the `ErrorJSON` generated by Phoenix. The pipeline has been there since the generator; the door was never opened.

That is good — greenfield is where the decision is cheap. And it is dangerous for the reason the security assessment measured: **every access guarantee of this platform lives in the `:browser` pipeline or in the `on_mount` of the `live_session`s**, and the `:api` pipeline goes through neither.

Nine guarantees the API does **not** inherit: an authenticated person; the tenant coming from the account and never from a parameter; a versioned session; expiry from inactivity; a temporary password forcing a change; an increasing wait at sign-in; a single refusal message; operational reach; CSRF.

**The API is not a screen without HTML.** It is a second door to the same data, and each of the nine has to be rebuilt or explicitly waived with a written reason.

### The pressure that exists, and why it does not decide

Whoever wants the same number in their own dashboard, in a spreadsheet or in an agent has no way in. It is a legitimate and old request. But the whole platform exists to separate what was **observed** from what was **derived** and from what was **declared**, and a response that delivers a number without that mark destroys the distinction exactly at the point of delivery.

## Decision

**Open a read-only HTTP API, authenticated by token, in which the token identifies *who* and *where* — and nothing else.**

Five decisions make up this one, and each exists to close a path:

### 1. The token carries no permission. None.

It keeps `user_id` and `tenant_id` (`NOT NULL`). *What it may do* is **recomputed on every request** by `Tenants.Access` — `scopes/2`, `pode_ver/3`, `pode_ver_equipe/3` —, which is the verdict the screens already use.

**The consequence that is the main gain**: five events take effect on the next request with no additional work — a grant revoked, a team membership ended, a link revoked, a role demoted, the tool's observation ended. `access.ex` already says why: *"the fact ended, the scope closed — no job, no column, no second truth"*.

**What this forbids**: JWT with *claims*, a token with embedded scopes, any verdict materialized in the token's row. They would create the second truth about access that `access.ex` was written not to have — and it **ages in the pocket of whoever has left**.

### 2. v1 is read-only

Writing stays out because the platform records `declared_by_user_id` and **there is no honest author** for an act a program performs. It is not a technical limitation: it is provenance being taken seriously at the point where it costs.

### 3. The secret is stored with an irreversible hash, and compared in constant time

SHA-256 of the secret with `Plug.Crypto.secure_compare/2`. The database lookup is by the indexed **public id**, and the hash check is in memory.

### 4. No threshold in a module constant

Validity, expiry from disuse, expiry warning, page ceiling and rate limit live in `priv/knowledge_base/rules/api_access_thresholds.yaml`. FR-069, and here with a security consequence of its own: an expiry period hidden in an attribute is a decision about risk that nobody reviews.

### 5. No token cache

Revocation applies on the next request. A cache comes back as a decision, if and when the cost becomes a **measured** problem, with a declared invalidation period.

## Alternatives considered

| Alternative | Why not |
|---|---|
| **Token with embedded scopes (JWT)** | recomputing per request costs one query; embedding costs **the second truth**. A token issued in January asserts, in March, a reach the organization has already undone. Rejected for the reason decision 1 explains |
| **A tenant token, not an account token** | it would give a stable integration when the person changes team. But the request is *"only authorized people"*, and without `user_id` the sentence loses its subject: there is no one to apply `pode_ver/3` to |
| **Storing the token encrypted with Cloak** (the house standard for secrets) | it is the right standard for a **third party's** credential, which the platform needs to recover to call GitHub. Here the value is never used back, only checked — storing it reversibly would keep a recoverable secret **with no use for the recovery**, and with the master key it would give all of them back |
| **Bcrypt, like the password** | the ~100 ms are the protection of a low-entropy secret chosen by people. On a 32-byte machine-generated secret there is no dictionary to go through, and the cost becomes a self-inflicted denial of service |
| **OAuth with the person's account** | it is the path a client such as claude.ai expects, and it is more work. It is left for when there is a consumer that requires it — and it will be a new ADR, not a bigger version of this one |
| **Not opening an API; offering file export** | it solves the spreadsheet and does not solve the dashboard or the agent. And an export without the origin mark has the same defect as the API without it, with less control |

## Consequences

### What improves

- the old request is met without duplicating the access model;
- [spec 062](../../specs/062-servidor-mcp/spec.md) stops being blocked — the MCP server backlog item said *"depends on deciding authentication and tenant"*, and this is it;
- the single verdict gains a second consumer, and with it a parity test that does not exist today: what the screen refuses, the API refuses. Divergence becomes detectable.

### What gets worse, and is accepted

- **one more query per request** to recompute the reach. It is the price of not having the second truth, and it is the inverse of the trade-off JWT proposes;
- **the integration's reach changes when the person changes team**, and whoever integrates may not understand why. The screen has to make this visible;
- **the attack surface really grows.** Ten high-severity findings in the assessment, and nine guarantees to rebuild.

### What this decision exposes without introducing it

**There is no disabled-account state on this platform.** `users` has `email`, `name`, `role` and `tenant_id`; `tenants` has `status`, `users` has no equivalent. The accounts screen offers create, reset password, associate and revoke link — there is no disable.

Offboarding today is implicit: whoever administers resets the password, receives the temporary one once, and does not hand it over. **That mechanism stops working the day a token exists** — the token is not the password, and changing the password does not invalidate it.

A person who leaves the organization would keep reading its data through the API, and whoever administers would have no act that solves it. `users.disabled_at` is a backlog item **prior** to this feature; while it does not exist, bulk revocation per account (FR-074 of 061) is the substitute, and the limitation is written in the API documentation.

## What is missing before the code

This ADR does not authorize implementation. Under the house rules, what is missing is: `plan.md`, `tasks.md`, a sprint backlog opened by its own skill, and confirmation of this ADR by the maintainer — the status above is **Proposed**.
