# The application serves with less power in the database

Until now, the application that serves the screens, the API and the collection used, in the database, the same access that
creates and alters the structure of the tables. With this change, there are two separate accesses: one that
**alters the structure**, used only when a version is published, and another, with less power, that
**serves** — reads and writes the data, and nothing beyond that. The integrity rules that the database itself
guarantees, such as the record that only accepts additions, are no longer within reach of what serves. This is a
page for whoever operates the platform: whoever only uses it sees no difference at all.

## What you can now do

**Those who use it: nothing changes on screen.** No screen, no label, no person's permission changes.
Who sees what is still decided by the same rules as before. What changes is invisible: the application
that serves you now runs with less power in the database, and so the guarantees the database gives
keep holding even if something inside the application fails.

**Those who operate it: publishing still runs on its own.** Publishing a version still applies the
database structure changes in the deploy itself, with no manual step each time. The difference is that this stage
uses the access that alters the structure, and the application left running after it no longer has it.

**Those who operate it: one step, once.** The separation only takes effect in production after whoever operates
creates the two accesses and configures the credentials in the deployment panel, following the operations
runbook. The values are generated by whoever operates, and do not go through chat, commit or message.

**Those who operate it: knowing whether it is in effect.** The platform does not assume the separation is in effect just
because the configuration exists: it checks in the database itself, and says whether it is in effect, whether it is not, and
why.

**The backup remains restorable.** A copy made before the switch can be restored after it, and
the application serves again with the lower-power access, with no manual adjustment.

## What the screen refuses, and says why

There is no screen, and therefore no visible refusal. The only situation whoever operates notices is in the deploy:
if the credential that alters the structure is not configured **and** there is a structure change to
apply, the new version does not come up — instead of serving on a half-migrated database. With no pending change,
it comes up normally.

## What it does not do

- **It does not change what each person can see or do.** The permissions of those who use it are the same; this
  change is about what the application can do with the database, not about what people can do
  with the application.
- **It does not take effect on its own in production.** Until whoever operates follows the runbook, the platform keeps
  working as before, and the check says the separation is not in effect.
- **It is not in production.** It is in `development`, with no release and no recorded acceptance.
