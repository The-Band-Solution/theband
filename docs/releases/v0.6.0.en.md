## Why 0.6.0 — and why not 1.0.0 nor 0.5.1

**MINOR, because the release delivers new user stories and withdraws no promise.** It is not
PATCH: US1 to US5 and US9 of feature 060 did not exist in v0.5.0, and PATCH is a fix that does not change
what was promised. It is not MAJOR: nothing anyone uses stopped being valid.

**Five of them are accepted** — US1, US2, US4, US5 and US9 (US1 and US9 reassessed on
2026-09-09). US3 shipped and is **not** accepted. That does not change the version number: MINOR
requires delivering a new user story, and five accepted ones satisfy that with room to spare. It changes what the
release may **declare** as content, and that is what the section *What was left out* does.

Three changes to existing behavior were weighed one by one, because that is where the
decision is won or lost:

| What changed | Why it is **not** a contract break |
|---|---|
| **the write-permission model on the structure.** `pode_declarar_estrutura/4` went out, `pode_gerir_estrutura/3` came in: the account scope stopped deciding writes and started deciding the role grant | **measured before switching: zero accounts lose write access** (T006, recorded in [#821](https://github.com/The-Band-Solution/theband/pull/821)). The account scope still decides **visibility**. No existing account loses capability — the rule behind it is a different one, and that is written down. **The measure is from development, and repeating it in production is a precondition of the delivery** (below, step 4) |
| **two amendments to published features** — 057 FR-011 (which forbade charts on the composite team screen) and 057 FR-029 / 055 FR-013, recorded in [`spec.md` §emendas](../../specs/060-tela-da-equipe/spec.md) | both **lift a prohibition**: the composite team gets the charts it did not have, and the operational definition of *promised* becomes mandatory next to the title. Whoever used the screen gains; nobody loses. The per-sub-team table still has no chart, which was what 057 protected |
| **`MAINTAINER` left the team screen** | it was **an administration access level on GitHub presented next to a role column** — and read as a role by anyone skimming. No longer displaying it removes a **false statement**, not a promise: the screen's promise is *who is on the team and what role they play*, and `MAINTAINER` was never a role. The data is still stored. **That it currently appears on no screen at all is a pending item, and it is named below** |

And the one that changes an **internal contract**: `count_team_members_at/3` and `team_members_at/3`
started counting **distinct people** where they used to count team memberships. It is not a break — it is the
function starting to honor what its name promises. But **it changes numbers someone may
have written down**: for a person with two roles, the total used to be 2 and is now 1.
Evidence of the fix: `test/the_band/ontology/seon/eo/promocao_de_evidencia_test.exs:239`
— *"uma pessoa com dois papéis conta UMA vez"* ("a person with two roles counts ONCE").

**About 1.0.0, explicitly.** MAJOR here would be `1.0.0`, and in semver `1.0.0` is the
declaration that the public contract is stable. This release **cannot** make that
declaration: **the public API does not exist as code** — three of the nine user stories of the very
feature this release carries have no task, and the permission measure it depends on was not
repeated in production. Buying a version number to pay for a rule change would say about the
product something that is not true. Semver §4 is the text: in `0.y.z` the public contract is not
stable, and an incompatible change fits in MINOR.

## Verdict per user story

**The classification follows from the criteria**, never from the merge and never from the marking in
`tasks.md` (`sro.rule03.deliverable_acceptance_by_criteria`). The user stories assessed
are the **atomic** ones materialized by this release's deliverables.

**What counts as evidence here**: a named assertion in the repository, and the verdict of
`mix gates` **read from the log**. What does **not** count: the `[x]` marking in `tasks.md`, which is
a declaration by whoever implemented.

**Limitation of this assessment, declared**: I did not run the suite — the `EXIT=0` with 1,926
tests is what [#821](https://github.com/The-Band-Solution/theband/pull/821) reports
as read from the log, and no independent review confirmed it (see *The review gap*).
What I confirmed file by file is the **existence of the assertion** each criterion requires.

## Accepted residual risk — the `decimal` exception

**Decision: accepted.** `hex: [ignore_advisories: ["CVE-2026-32686"]]` ships in `mix.exs`.

**And what I am accepting is not the risk.** It is the divergence between the advisory database and the
installed artifact. The reach assessment
([`docs/seguranca/2026-09-08-decimal-expoente-ilimitado.md`](../seguranca/2026-09-08-decimal-expoente-ilimitado.md))
measured on the artifact, it did not deduce: the default context of `decimal` 3.1.1 is born with
`emax: 6144`, `Decimal.parse("1e1000000000")` returns `:error`, and the OSV record itself
declares the affected range as `< 3.0.0` — it matches 3.1.1 only because its SEMVER range
**has no `fixed` event**. The mitigation the advisory asks for is already installed.

Four reasons, and the fourth is the one that decides:

1. **there is no exploitation path.** `Decimal` appears in one line of code
   (`lib/the_band/work_items/person_work.ex:478`), behind `require_user`, the `on_mount`
   and `Tenants.pode_ver/3`. There is no `numeric` column, `:decimal` field, nor JSON endpoint;
2. **no gate is weakened.** The exception is **by ID**: it does not change severity, does not
   turn off the gate, does not affect another package, and the finding is still printed in
   `Ignored advisories:` on every run. Sobelow's `--exit low` does not change, and no
   step leaves `lib/mix/tasks/gates.ex`;
3. **the tool denounces the obsolete entry.** Measured: with an ID that does not match,
   `mix hex.audit` warns that the entry *"can be removed"* and keeps `EXIT=1`. The exception
   shouts on its own when it stops being true, instead of going silent forever;
4. **the real protection is not the exception — it is the test.**
   `test/the_band/decimal_limitado_test.exs` fails if the `Decimal` range stops being
   the fixed one. A downgrade breaks the **suite**, which is where the regression should show up, and
   does not depend on someone rereading a date. Without that test I would refuse: the exception alone
   would trade a false positive for a blind spot.

**Deadline**: until the OSV/EEF record gets the `fixed` event, and **at the latest until 2026-12-07**
(90 days), when the entry is re-examined even if nothing has changed. Reassessment
mandatory at the close of each sprint while it lasts.

**Signals that force a reassessment before the deadline** — any of them: `mix hex.audit` warning
that the entry no longer matches; a new version of `decimal` published on Hex (update and
**remove the exception** before anything else); a new route outside `require_user` that
accepts a number as text; a new `:decimal` field or `numeric` column; or any call that
loosens `emax`/`emin`.

**What I refused**: building automatic expiry into `mix gates`. It would be new code in
privileged code to solve a third party's metadata problem, and `mix gates` is the
single definition of the gates. Less code, more evidence.

**What remains open, and is not for this release**: finding 2 of the assessment —
`person_work.ex:478` calls `Decimal.round/2` without an explicit limit and without error
handling, with the guarantee living two layers below, in the Postgres protocol's `int16`.
Severity **low**, no exploitation path today. It goes to the product backlog as an FR with a
task: the §7.1 guard test plus a comment saying **where** the guarantee comes from.

### The waiver of step 7, and what it costs

mistake on a team starts to see the whole structure **without any button**, and the named refusal
says *"No role of yours is granted to manage this team's structure"*. The way back is not
a rollback: it is granting management to that account's role in `/roles`.

**The query, to run when there is access** — it is the same one T006 used:

```sql
SELECT count(DISTINCT u.id)
  FROM users u
  JOIN tenant_access_scopes s
    ON s.user_id = u.id AND s.scope = 'organization' AND s.revoked_at IS NULL
 WHERE u.role <> 'admin'
   AND NOT EXISTS (
     SELECT 1
       FROM eo_people p
       JOIN eo_team_memberships m
         ON m.person_id = p.id AND m.ended_at IS NULL AND m.invalidated_at IS NULL
       JOIN eo_role_structure_management_grants g
         ON g.organizational_role_id = m.organizational_role_id AND g.revoked_at IS NULL
      WHERE p.id = (SELECT person_id FROM tenant_person_links
                     WHERE user_id = u.id AND invalidated_at IS NULL LIMIT 1)
   );
```

Zero means nobody lost write access. Greater than zero **names** who lost it, by replacing
`count(DISTINCT u.id)` with `u.email`.
