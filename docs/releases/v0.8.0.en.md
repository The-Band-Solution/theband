**The `issues` phase of collection went to version 5, and that reopens the incremental cut in all
repositories on the first collection after the deploy.**

### The new migration is additive

```

  add :password_source, :string
  add :password_set_by_user_id, :binary_id

execute "INSERT INTO account_disablements ... FROM users u WHERE u.disabled_at IS NOT NULL"
```

**In `up`, no `drop`, no `modify`, no column removed** — and an `execute INSERT` that
fills `account_disablements` from `users.disabled_at IS NOT NULL`, with
`disable_reason = 'not_recorded'`. Additive.

**"Rollback without loss" only holds for what existed before** (corrected on 2026-09-13). The `down` does
`drop table(:account_disablements)` and `remove` of the two columns: each disablement episode
written **after** the deploy — reason, note, author, re-enablement — is lost in a rollback;
`users.disabled_at` stays. It is not a reason not to ship; it is what a rollback costs, written before
it is needed.

## How to execute

There are **two PRs**, in this order — and neither of them is the deploy on its own:

1. **the bump**: `chore/release-v0.8.0 → development`, squash. It takes `mix.exs` to 0.8.0 and this
   document. It is the step that comes **before** the release PR, as in v0.7.0 (#851). It is **#916**,
   and at 21:09Z on 2026-09-13 it was **without a requested reviewer and outside the project** — the house rule
   requires both on opening. It is fixed before the merge:
   `gh api -X POST repos/The-Band-Solution/theband/pulls/916/requested_reviewers -f 'team_reviewers[]=the-band'`,
   and checked with `gh pr view 916 --json reviewRequests` (empty list = nobody was requested);
2. **the release**: `development → main`, **merge commit** — never squash. L83: squash makes the
   two lines diverge, and the divergence cannot be undone.

```bash
gh pr create --base main --head development --title "Release v0.8.0"
# depois da aprovação, por comando — o botão não tem método default:
gh pr merge <n> --merge
```

**The tag is not created by hand.** It is born from the CD on the push to `main` (`.github/workflows/cd.yml`,
step *a tag git nasce do merge*), and the first step of the same CD **fails, naming it** if
`v0.8.0` already exists on another commit. Creating the tag beforehand would fail the deploy itself.

After the deploy, the **first** measurement is `/version` — and it becomes possible for the
first time. The CD already does it: *a produção confirma a versão — resposta diferente FALHA*.

**The moment of delivery is the Product Owner's decision** (FR-016). This document assesses and
prepares; it does not authorize.
