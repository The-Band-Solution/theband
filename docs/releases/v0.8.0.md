## Riscos, medidos

### A migração nova é aditiva

Uma só desde o PR #852: `20260910050000_episodio_de_desativacao.exs`.

```
alter table(:users) do
  add :password_source, :string
  add :password_set_by_user_id, :binary_id
create table(:account_disablements, ...)
create index(...); create unique_index(..., where: "enabled_at IS NULL")
execute "INSERT INTO account_disablements ... FROM users u WHERE u.disabled_at IS NOT NULL"
```

**No `up`, nenhum `drop`, nenhum `modify`, nenhuma coluna removida** — e um `execute INSERT` que
preenche `account_disablements` a partir de `users.disabled_at IS NOT NULL`, com
`disable_reason = 'not_recorded'`. Aditiva.

**"Rollback sem perda" só vale para o que existia antes** (corrigido em 2026-09-13). O `down` faz
`drop table(:account_disablements)` e `remove` das duas colunas: cada episódio de desativação
escrito **depois** do deploy — razão, nota, autor, reativação — se perde num rollback;
`users.disabled_at` fica. Não é motivo para não subir; é o que um rollback custa, escrito antes de
precisar.

### As variáveis novas não bloqueiam a subida

As cinco `MINIO_*` entraram no `.env.example`, e todas têm padrão no `compose.yaml`
(`${MINIO_ROOT_USER:-theband}`, `compose.yaml` l.128-163). Vivem no profile `backup`.

**Nenhuma variável obrigatória nova.** As exigidas (`${VAR:?}`) no `compose.yaml` seguem as três
de sempre — `DATABASE_URL_CONTAINER`, `SECRET_KEY_BASE`, `THE_BAND_MASTER_KEY` — e o arquivo só
ganhou linhas no intervalo (+74, −0). A lista fechada do contrato do pipeline não mudou.

A branch de release acrescenta mais três ao `.env.example` — `PRODUCAO_URL`,
`PRODUCAO_TESTE_EMAIL`, `PRODUCAO_TESTE_SENHA` —, lidas só pelo agente `aceitacao-em-producao`;
o `compose.yaml` não as referencia. Sem elas o agente roda e declara o que não mediu.

**"A produção não usa o profile `backup`" não foi medido**: a configuração do Dokploy não é
acessível daqui, e a afirmação anterior desta seção vinha de memória. Há decisão em curso — o PR
**#914**, aberto, propõe MinIO como destino de produção.

### O que muda de comportamento em tela já em uso

- **a listagem de itens ganha uma oitava coluna.** Em tela estreita, a rolagem lateral fica
  mais frequente. Não esconde nada — é custo de leitura;
- **a tela de contas passa a distinguir desativada de recém-criada.** É correção: antes as
  duas eram iguais;
- **o detalhe do item ganha repositório nas sub-listas.** Cinco vínculos em 1 953 mostram a
  marca `other repository`; os outros ganham só o caminho.

## Como executar

São **dois PRs**, nesta ordem — e nenhum deles é o deploy sozinho:

1. **o bump**: `chore/release-v0.8.0 → development`, squash. Leva o `mix.exs` a 0.8.0 e este
   documento. É o passo que vem **antes** do PR de release, como na v0.7.0 (#851). É o **#916**,
   e às 21:09Z de 2026-09-13 estava **sem revisor pedido e fora do projeto** — a regra da casa
   exige os dois ao abrir. Corrige-se antes do merge:
   `gh api -X POST repos/The-Band-Solution/theband/pulls/916/requested_reviewers -f 'team_reviewers[]=the-band'`,
   e confere-se com `gh pr view 916 --json reviewRequests` (lista vazia = ninguém foi pedido);
2. **a release**: `development → main`, **merge commit** — nunca squash. L83: squash faz as
   duas linhas divergirem, e a divergência não se desfaz.

```bash
gh pr create --base main --head development --title "Release v0.8.0"
# depois da aprovação, por comando — o botão não tem método default:
gh pr merge <n> --merge
```

**A tag não se cria à mão.** Ela nasce do CD no push em `main` (`.github/workflows/cd.yml`,
passo *a tag git nasce do merge*), e o primeiro passo do mesmo CD **falha nomeando** se
`v0.8.0` já existir em outro commit. Criar a tag antes reprovaria o próprio deploy.

Depois do deploy, a **primeira** medida é `/version` — e ela passa a ser possível pela
primeira vez. O CD já a faz: *a produção confirma a versão — resposta diferente FALHA*.
