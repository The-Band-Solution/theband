## The version, and why

**v0.11.0, MINOR.** The release delivers capability that did not exist without breaking what the API
promised to whoever uses it.

| Degree | Carries it? | Why |
|---|---|---|
| MAJOR | **no** | no legitimate contract breaks. The three numbers that change for integrators (`/measures` of a composite team, `access.reason`, the `404` in JSON) are the code coming to meet what the contract **already** said: *"one definition of who belongs here"* (061), the `vinculo_vigente` vocabulary already published in the OpenAPI, and 061's FR-020, *"um formato único para todos os códigos"* ("a single format for all codes"). Signing in again once is not an API contract: it is a screen session, and the API token does not drop |
| **MINOR** | **yes** | `boards` on each open task, in the API and the MCP (062/FR-033); the 90-day retention of sessions, with a daily job; `TheBand.Release.encerrar_todas_as_sessoes/0`, which whoever operates runs inside the release; `mix the_band.varre_segredos` and `mix the_band.confere_encerramentos`, for whoever operates and for `mix gates` |
| PATCH | also, and absorbed | the 064 security fixes and #1015, #1017, #1018 and #1020 alone would be PATCH. In a release that carries MINOR, they do not raise the number |

The series is `0.x`, and the decision above does **not** rely on that: the notes of this house apply
the table to `0.x` as if it were stable (see `v0.10.0.md`).

## 064 — secret at rest

**What the person now has**, said for users: The Band's database stops keeping anything that opens a
session, and so a copied backup, even together with the server's key, is no use for impersonating
anyone. Signing out now means signing out.

Four migrations, all from this feature. The detail of each is in *The risks measured*.

### #1004 — the model provider's key travels sealed up to the header (064/T006)

**What it delivered**: the model provider's key is now wrapped in `TheBand.Segredo` where it is read
(the tenant's credential, the form, the environment's `API_KEY`) and is only opened in the header and
in error redaction. An error along the way now shows `#Segredo<…[redigido]>`, and not the key. It is
the same class as the defect of 2026-09-04, in which a `FunctionClauseError` left a GitHub token in
clear text in `oban_jobs.errors` for eight days; the GitHub path was closed by #864, and this one was
still open. Guard proven by reinjection: with the key as a bare binary, the same error leaks. Closes
#871.

### #1005 — the secret scan, with a positive control (064/US1)

**What it delivered**: `mix the_band.varre_segredos --dump <arquivo>` and `--banco`, which look for
clear-text secrets in a dump or in the database **before** each copy of the backup. The report says
what it looked for, proves with the positive control that it saw each pattern, and says **where** it
found, never **what**; the control that fails exits with `2`. The session token, which has no prefix,
is looked for only in `users.session_token`, because in the development dump its shape matched 5,928
times for 2 true ones. The dev database was scanned: 0 GitHub tokens, 0 provider keys, 2 session
tokens in `users.session_token` — the finding of US2. An exception in `sobelow` only for
`Varredura.dump/2`, decided by the maintainer on 2026-09-28, with a guard that fails if it appears in
another function. Closes #866 to #870.

**It does not run in production**: the release has no `mix`. [redigido]

### #1006 — the terminal job without an end date stops being permanent (064/US3, T007 and T008)

**What it delivered**: the migration that fills null `cancelled_at` and `discarded_at` in
`oban_jobs` with the latest date of the record, capped at now, and marks in `meta` what it filled, so
that the `down` is exact (T007); and `mix the_band.confere_encerramentos`, which fails if a terminal
job without a date comes back, without printing `args`, `errors` or `meta`, and is part of
`mix gates` (T008). Oban's pruning compares that date with the cutoff, and `NULL` is never less than
the cutoff: the job that failed escaped pruning forever, and it is the one that tends to carry a
secret. In dev there were four, one of them with a secret. Closes #872 and #873.

### #1010 — the US2 security assessment, decisions P1 to P6, and the additive base (T009, T010)

**What it delivered**: the US2 security assessment, done before the code by the `security` agent,
which did not write the design (`specs/064-segredo-em-repouso/seguranca-us2.md`, 15 findings, two
high); the six decisions of the maintainer of 2026-09-28, one of them P1, which is the reason for the
notice at the top; the `user_sessions` table, with only the token's digest in `bytea`, `tenant_id`
with a composite FK and no `last_seen_at` (T009); and `users.password_epoch`, which goes up atomically
in the five paths that set a password (T010). Nothing anyone would see. Closes #874 and #875.

### #1011 — sessions open, check and end through the new table, and disabling ends them (T011)

**What it delivered**: `TheBand.Tenants.Sessions`, with `abrir/1`, `conferir/2`, `encerrar/1`,
`encerrar_da_conta/2` and `girar_todas/0`. The check looks up by primary key and compares the digest
with `secure_compare`, as ADR 0010 does with the API token; the validity is 7 days from the opening
of **this** session; and the password epoch is checked in the same query. Disabling an account now
ends its sessions in the same transaction, and re-enabling it does not give them back (S1). Closes
#876.

### #1012 — the session is now read from `user_sessions`, and everyone signs in again (T012, T013)

**What it delivered**: `TheBandWeb.Sessao`, the single point that reads and writes the cookie, used
by the plug, by the LiveView hook and by the controller; the cookie now carries `session_id` and
`session_secret`, and no longer `user_id` and `session_token`. Signing out calls
`Sessions.encerrar/1` before dropping the cookie (S5); `set_password` no longer has its own door
(S3); a cookie with only `user_id` opens nothing (S4); the validity holds in the plug and in the
hook, through a single point (S6). The T012 migration rotates `users.session_token` of **every**
account, in pure SQL, so that no value that was ever in a backup matches again (S7) and so that a
rollback does not open the old sessions either. **It is this PR that forces everyone to sign in
again.** Closes #877 and #878.

It is the US2 PR that its own body says most calls for human reading, because it changes how every
authenticated request is accepted. See *The review*.

### #1013 — sessions that stopped being valid 90 days ago leave the table (T020)

**What it delivered**: `Sessions.apagar_as_que_deixaram_de_valer/1`, the single path that deletes,
and the `ApagaSessoesAntigas` worker in Oban's Cron, `0 4 * * *`. Two conditions: ended more than 90
days ago, **or** opened more than 97 ago (7 of validity plus 90), because a session that expired
without anyone ending it has no `ended_at` and would stay forever. Decision P3: kept forever, the row
would be a history of the person's activity in every backup. Closes #1007.

The time zone of 04:00 is that of Oban's Cron, which `config/config.exs` does not pin; it was not
measured in production.

### #1014 — what a restore does to the sessions, and the command that ends them all (T015, T016)

**What it delivered**: `docs/producao/runbook.md` §10.1 answers *"what happens to the sessions if I
restore a backup?"*, including the case that surprises — a session ended between the copy and the
disaster **becomes valid again**, and a password changed after the copy goes back to being the old
one —; and §10.2 makes it **mandatory** to end all sessions after restoring (decision P5), with the
command that runs without `mix`:

```bash
/app/bin/the_band eval 'TheBand.Release.encerrar_todas_as_sessoes()'
```

The command only says **how many** sessions it ended. Closes #880 and #881.

### #1015 — the session cookie comes out with `Secure` in production (#1008)

**What it delivered**: `config :the_band, :cookie_de_sessao_seguro, true` only in `config/prod.exs`,
read at compile time by the endpoint. Without `Secure`, the browser sent the cookie over HTTP on the
first request, before the `force_ssl` redirect. It is finding S15, low. No new environment variable.
The real confirmation only exists in production, and is in *After the merge*. Closes #1008.

## 062 — the MCP server

### #1001 — each open task says which board it is on, with which values (062/FR-033)

**What the person can now do**: ask the agent, or the API, which board each open task of a person is
on and with which values — `Squad: Green`, `Status: In Progress` —, and not only that it is open.
`team_open_work` and `GET /api/v1/teams/:id/measures` get `boards` on each task: one entry per board,

## Fixes

### #1017 — the composite team's work counts the team and the parts (#987)

**What it delivered**: in a composite team, `work` and `open_by_person` in `/measures` and the
`team_open_work` tool now count the team and the parts with in-force composition, each person and
each task once — union, not sum —, and the MCP stops asserting `is_composed: false` for a team that
has parts. **It had been live since v0.10.0**, and its note listed it as a known defect: on dev's
`LEDS - ConectaFapes`, `team_roster` counted 48 members and `team_open_work` 31. The sub-team cards
on the screen do not change. Closes #987.

**The numbers integrations receive change** for composite teams. In the same `/measures` response,
`time_to_first_review` and `skills` keep counting only the direct members; that is #1016, which PR
#1021 closes (see *The last fix before the release*, below).

### #1018 — whoever belongs to the team is recorded as `vinculo_vigente` (#985)

**What it delivered**: a team member is now recorded as `vinculo_vigente`, and not as
`escopo_de_equipe`, in the `access.reason` of `GET /api/v1/teams/:id`, in the access log and in the
MCP. **The verdict does not change**: whoever saw keeps seeing. The scope clause counted the scope
derived from the team membership itself, and the `vinculo_vigente` clause was dead code. Whoever
belongs **and** received a scope is recorded by the grant. Previous access records are not
rewritten, and keep saying `escopo_de_equipe` for members. Closes #985.

### #1020 — a nonexistent path in `/api/v1` answers `404` in JSON (#943)

**What it delivered**: `GET` or `POST` on a path that does not exist under `/api/v1` now answers
`404` with `code: "not_found"` and `request_id`, in FR-020's single format, and not the site's HTML
page. Without a token, `401`, like any other path. The wildcard does not appear in the OpenAPI. A
nonexistent `/mcp/*` was not touched. Closes #943.

### #1024 — the issue detail shows the labels with the source of each one (#904)

**What it delivers**: in the issue detail, the labels field now uses the same grammar as the `/work`
list. The field's label appears **solid**, and the one read from the title prefix appears
**hatched with an outline**. The source comes **written**, one line per source, and all labels
appear. When there is none, the screen says whose each half of the absence is. It fixes defect D1
of the acceptance of 065/US1: the list showed `backend` and `Devops`, and the detail only `backend`,
with no source. The prototype was approved by the maintainer on 2026-09-29, and is in
`specs/065-rotulos-no-item/prototipo/`.

It **does not close** #904: US1 closes on acceptance, which can now be redone. Normalizing the case
of the prefixes was left out and became feature #1023.

### The four migrations

| Migration | Task | What it does | Does it go back? |
|---|---|---|---|
| `20260928200000_preenche_datas_de_encerramento` | T007 | `UPDATE` on `oban_jobs`: fills null `cancelled_at`/`discarded_at` and marks in `meta` | **the `down` is exact, and it is no use in production.** Oban's pruning (`max_age` of 7 days) deletes, on the next pass, minutes later, the jobs filled with an old date. | `20260929100000_sessoes_de_usuario` | T009 | creates `user_sessions` | additive; `down` removes the table |

**About T007 in production, what cannot be done beforehand.** PR #1006 warned: if one wants a record
of which jobs existed in production without an end date, and with what, it has to be made **before**
the deploy. The release has no `mix`, so neither `confere_encerramentos` nor
`varre_segredos --banco` run there, and there is no ready command inside the release for it. It is
not loss of data anyone uses: they are jobs that failed and that pruning should already have deleted.
But it is the last chance to know how many there were.

**Not measured, by decision of the maintainer on 2026-09-29.** The first decision was to count
beforehand, read-only. The session that prepared the release had no access to the production
database: reading the SSH configuration was refused by the permission control, and there was no
attempt to get around it. Faced with that, the maintainer decided to proceed without the count. The
query is recorded for whoever wants to measure **before** the merge; after it, pruning will already
have deleted the jobs:

```sql
SELECT state, count(*)
  FROM oban_jobs
 WHERE (state = 'cancelled' AND cancelled_at IS NULL)
    OR (state = 'discarded' AND discarded_at IS NULL)
 GROUP BY state;
```

**Result in production:** not measured.

**The restore rehearsal** (`docs/producao/runbook.md` §6) now requires the §10.2 step after
restoring. It is not a precondition of this release: none of the migrations deletes domain data.

## After the merge

The order, and whose each step is. No agent in this session accesses production.

0. **before the merge**: tell users they will need to sign in again. The count of jobs without an end
   date **was not measured**, by decision (see *The four migrations*);
1. **the CD publishes and delivers**: the merge into `main` creates the `v0.11.0` tag, publishes
   `ghcr.io/the-band-solution/theband:v0.11.0` and calls the Dokploy webhook. Nobody builds,
   tags or publishes by hand;
2. **the version live**, from the source and not from `mix.exs`:

   ```bash
   curl -s "$PRODUCAO_URL/version"   # tem de responder 0.11.0
   ```

   While it answers `0.10.2`, nothing below starts;
3. **the `deploy-producao` agent** follows the delivery and checks health after it;
4. **the `aceitacao-em-producao` agent** measures what is measurable without an account:

   | What to measure | How | Possible verdict |
   |---|---|---|
   | the version | `curl -s "$PRODUCAO_URL/version"` → `0.11.0` | measurable |
   | `Secure` on the cookie | `curl -si "$PRODUCAO_URL/sign-in"` and, if the response does not bring `_the_band_key`, #1015's command: `curl -si -X POST "$PRODUCAO_URL/session" -d 'identifier=x&password=y'`; in both, `Set-Cookie: _the_band_key=…` has to carry `secure` | measurable **if** some anonymous response sets the cookie; if none does, **not measurable** |
   | the `404` in JSON, anonymous side | `curl -si "$PRODUCAO_URL/api/v1/nao-existe"` → `401` with `content-type: application/json`, and **not** HTML | measurable |
   | the `404` in JSON, with a token | `GET /api/v1/nao-existe` with a token → `404`, `application/json`, `error.code = "not_found"`, `request_id` | **not measurable** by the agents: there is no production token |
   | signing in again works | sign in with a real account, sign out, and see the old cookie refused | **not measurable** by the agents: there is no acceptance account (decision of 2026-09-24). The maintainer can attest, with the date and the sentence |
   | `boards`, `vinculo_vigente`, the composite team | authenticated API and MCP | **not measurable** |

   The authenticated side stays **"not measurable", never "accepted"**;
5. **the inherited searches** for who may have seen it, if they have not been done yet, with the
   result recorded in the note of origin;
6. **back-merge** from `main` to `development` through `back-merge/v0.11.0`, created from
   `origin/main`, by merge commit (L92, #998);
7. **open T014 (#879)** for the next release: it can only go after step 2 answers `0.11.0`.
