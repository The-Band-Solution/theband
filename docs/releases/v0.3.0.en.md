## Why this release exists now

**Because the own domain cannot be switched on without it.** v0.2.0 does not know
`THE_BAND_ORIGENS_EXTRAS`: publishing [redigido] against it would deliver an
address that answers 200 over HTTP and refuses the live connection — the page opens,
no screen updates, and no error appears. It is pending item P1 of 050, and it is
exactly the defect that 054 exists not to introduce.

The order, then, is: **this release first, runbook `§9` afterwards**.

## The exception, declared

The release record model says that **only accepted deliverables ship**. The
054 ships **without acceptance**, and the reason is structural, not haste:

> Two of its criteria — the socket accepted at both addresses (SC-002) and the
> foreign origin refused (SC-003) — **can only be measured in production, with the
> domain live**. And the domain can only go up against a version that knows the
> new variable. Requiring acceptance before the release would leave the feature
> permanently unassessable.

It is the same shape as 050, which also measured after publishing. What makes the
exception legitimate is that it is written down, together with what closes it:

**The acceptance of 054 happens after `§9`**, with `scripts/medir-enderecos.sh`
run at both addresses. Until that happens, this release carries
code whose behavior in production **has not been observed** — and what is
proven is the testable side: 23 tests, including the ones that fail if the absence of a
declaration starts letting things through.

## How to measure this release when it goes up

**This is the opportunity to close 050/US1**, which fell for lack of exactly
these three measures:

1. **open a session before** the deploy and check, afterwards, that it is still
   valid (AS4);
2. **time the window** between the last response of the old version and the first
   of the new one (AS5, SC-002 of 050);
3. **time the path** of opening the address, signing in and seeing a dashboard, from a
   network that is not the development one (SC-001).

Without someone with a clock at the moment of the merge, 050/US1 remains not accepted —
not because of a defect, but for lack of measurement.

## The own domain, live

[redigido] started serving on 2026-09-01, **not** through Let's
Encrypt: issuance failed with no diagnosed cause, and the path used was the
Cloudflare origin certificate with `Full (strict)`. It is recorded in
[runbook `§9-B`](../producao/runbook.md), including what it leaves open —
renewal stops being automatic.

**The measure that closes SC-002 of 054**, with the two addresses checked
separately:

| address | screen | plain http | socket, own origin | socket, foreign origin |
|---|---|---|---|---|
| [redigido] | 200 in 0.96s | 301 | **400** (accepted) | **403** |
| [redigido] | 200 in 0.85s | 301 | **400** (accepted) | **403** |

`scripts/medir-enderecos.sh` exited **0** at both.

And the certificate the browser sees at [redigido]: `CN=[redigido]`,
issuer `Google Trust Services` — the intermediary's Universal SSL, publicly
trusted.

**P1 of 050 was closed** by this release
([pendencias.md](../../specs/050-em-producao/pendencias.md)).

## What this release did NOT measure

The three measures that 050/US1 expects — session surviving the release (AS4),
unavailability window (AS5) and a path of under two minutes (SC-001) —
**remain without evidence**. The merge happened without someone with a clock, which was
the condition written here before it happened. #620 remains not accepted, and the
next release is the next chance.
