# v0.10.2 — hotfix: `mint` gets out of three CVEs, one of them high

**Hotfix**, and not a release from `development`. It is born from `main` (v0.10.1) and carries **one**
fix: the update of `mint`, the HTTP client through which the collection talks to GitHub. It goes back
to `main` and, through a `back-merge/v0.10.2` branch, to `development`, always by merge commit
(`AGENTS.md` §12).

**Proposed on 2026-09-28**, under the rule that security comes first (`AGENTS.md` §14.0).
**The moment of delivery belongs to the maintainer**: every merge into `main` is a deploy.

## Why it exists, and did not fit in v0.10.1

The `mint` update should have gone in v0.10.1 (#999). **It did not, because of a race**: #999 was
merged at 13:19:36 UTC on 2026-09-28, and the `mint` commit (`f779019`) was pushed afterwards, when
its gates finished, to a branch already merged. The CI of the merge into `main` failed on the
dependency audit, and that is how the gap showed up. The v0.10.1 note does not mention `mint`, so it
does not claim what it did not carry.

It is the same race as #995, on the same day: a commit pushed to a branch after its PR was merged.
The lesson is recorded, and this release closes the consequence.

`development` has had `mint` 1.11.0 since #1000.

## What was live

`mint` 1.10.1, with three advisories published on 2026-09-28:

| Advisory | Degree | What it is |
|---|---|---|
| EEF-CVE-2026-91043 | **high** | `cookie` fields indexed by HPACK in an HTTP/2 response get around `max_header_list_size`, and a malicious server makes the client allocate close to 1 GB per response |
| EEF-CVE-2026-92103 | medium | the HTTP/2 client buffers a frame of up to 16 MiB before applying `max_frame_size` |
| EEF-CVE-2026-94194 | medium | HTTP/1 applies *chunked* when it is not the final encoding, which allows response smuggling by an intermediary |

**Who the malicious server would have to be**: the other side of the connection, that is, the GitHub
API or something on the path to it. There is no evidence of exploitation; the update is by the rule,
and not because of an incident.

## The fix

`mint` 1.11.0, published on the same day, fixes all three and declares itself *"no breaking
changes"*. `finch` accepts it (`~> 1.8`). `hpax` goes up with it, from 1.0.4 to 1.1.0, because the
new `mint` requires it. Only `mix.lock` changes, besides the version.

## Why PATCH

| Degree | Carries it? | Why |
|---|---|---|
| MAJOR | no | no contract changes |
| MINOR | no | nothing new |
| **PATCH** | **yes** | it swaps a dependency for a fix version, with no interface change |

## The usual three risks

| Risk | Verdict | Measured as |
|---|---|---|
| destructive migration | **no migration** | `git diff origin/main -- priv/repo/migrations` empty |
| new mandatory variable | **none** | `config/runtime.exs`, `compose.yaml` and `.env.example` outside the diff |
| change in a screen in use | **none** | only `mix.lock` and `mix.exs` |
| dependency | **`mint` 1.11.0 and `hpax` 1.1.0** | the collection talks to GitHub through it; the same swap has run in `development` since #1000 |

## The evidence

- `mix hex.audit` and `mix deps.audit`: 0.
- `mix gates`: the exit code is on the PR.

## After the merge

1. the CD publishes the `v0.10.2` image and delivers it to Dokploy;
2. `curl -s "$PRODUCAO_URL/version"` has to answer `0.10.2`;
3. the CI of the merge into `main` has to be **green**, because it was what flagged the gap;
4. **back-merge** through `back-merge/v0.10.2`, created from `origin/main`, never with `main` as head.
