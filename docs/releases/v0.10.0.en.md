# v0.10.0 — three security fixes that are not live, and the MCP server

**Release from `development` to `main`**, and not a hotfix. `main` and production are on v0.9.2
(`/version` answers `0.9.2`); `development` is 37 commits ahead. Merge commit, never squash
(`AGENTS.md` §12, L83), and a **back-merge** from `main` to `development` afterwards, also by merge
commit, so that the release commit goes back into integration (L92).

**Proposed on 2026-09-27.** Decision of the maintainer on the same day: take production through the
**whole** release, and not through one hotfix per fix, because it carries **three security fixes
that are not live** (N5, H2-R and #989). Security comes first (`AGENTS.md` §14.0): active exposure
in production goes into the first possible release, and this is the first one. **The moment of
delivery belongs to the maintainer**: every merge into `main` is a deploy.

## The version, and why

**v0.10.0, MINOR.** The release delivers a capability that did not exist: an agent with the API
token can now ask about a team through `POST /mcp`, with four tools. Nothing the API promised to
those who **have** reach stops holding.

| Degree | Carries it? | Why |
|---|---|---|
| MAJOR | **no** | no legitimate contract breaks. The only response that changes shape is the one for whoever the verdict refuses, and what it carried was the defect itself. The decision is in *The API contract for whoever the verdict refuses*, below |
| **MINOR** | **yes** | the MCP server (spec 062): new route, four tools, `docs/api/mcp.md`. New functionality, no breakage |
| PATCH | also, and absorbed | the three security fixes and #941 alone would be PATCH. In a release that carries MINOR, the PATCH does not raise the number on its own |

`mix.exs` already says `0.10.0`, and was not touched by this note.

## The three security fixes

All three come from the same exercise: the security inventory done **before** 062
(`docs/seguranca/2026-09-24-inventario-antes-do-mcp.md`), because the MCP server reuses the token
door and serves data about people to another model. Two of them the inventory classified as
**blocking** for 062, and that is why they go in the same release as it, and before it in this note.

### #945 — suspending a tenant now also cuts its API tokens (finding N5)

**What it delivers**: the token door (`ApiAuth.com_tenant/2`) now checks `tenant.status`, as the
three session doors already did since #837. A token from a suspended tenant is refused with the
same body as the other refusals (SC-003), and the reason `organizacao_suspensa` goes to the log
(SC-004). Guard: `test/the_band_web/api/organizacao_suspensa_test.exs`.

**What was live, since v0.9.0**: suspending a tenant dropped the session and refused entry through
the screen, and did **not** touch the tokens. Measured in the inventory: the token answers `200`, the
tenant is suspended, and the same token keeps answering `200` on `GET /api/v1/people`. Every person
of the suspended tenant with an issued token kept reading people, teams, measures, projects and
syncs until the token expired, or never, for the *no expiration* token. Whoever suspended would
think they had suspended. Severity **high**.

**What the fix does not undo**: what was read after the suspension has already been read. The
question that matters is whether there is a suspended tenant in production, and the inventory
records that this **was not read** (item 3 of its limitations). To run in production:

```sql
-- Leituras por token feitas por organizações que hoje estão suspensas.
-- A base não guarda QUANDO a organização foi suspensa: tenants tem status, e não suspended_at.
-- O updated_at do tenant é só um teto aproximado: ele muda com qualquer alteração do registro.
SELECT t.id AS tenant_id, t.updated_at AS alterado_em,
       r.token_public_id, r.route,
       count(*) AS leituras, min(r.occurred_at) AS primeira, max(r.occurred_at) AS ultima
FROM api_access_reads r
JOIN tenants t ON t.id = r.tenant_id
WHERE t.status = 'suspended'
GROUP BY t.id, t.updated_at, r.token_public_id, r.route
ORDER BY ultima DESC;
```

**No rows**: no suspended tenant read by token, and N5 is left without consequence.
**With rows**: the reads after the suspension were improper; the exact date of the suspension is
not in the database and has to come from whoever suspended.

### #946 — the profile written by the model now follows the verdict, on the screen and in the API (finding H2-R)

**What it delivers**: the profile the model writes about a person (strengths, evolution,
"attention") and the counted competencies that come out of it now follow the same verdict
`pode_ver/3` as the work panel, at the three doors. Decision of the maintainer of 2026-09-24: **the
profile is aggregate**, and it became a row in the table of 045's FR-024.

| Door | Before | After |
|---|---|---|
| screen `/people/:id` | the `#profile` section for any account of the tenant | only with reach; without it, the profile is not even read, and the `gerar_perfil` event is refused in the handler |
| `GET /api/v1/people/:id` | `profile` always | `profile` is `null` without reach, and the note says **refusal**, not "no profile generated" |
| `GET /api/v1/people` | `competencies` of every person on the page | only of the people reached, with the page's reach in a single call (`pessoas_alcancadas/2`, L38) |

**What was live**: any authenticated account of the tenant read, on any person's page, the text a
model wrote about them; and any token read the counted competencies of everyone. Measured on the
screen in the inventory (a `member` account without a link, `{:nao, :sem_elo_declarado}`, the
profile's marks visible); **read, not measured**, in the API. Severity **high**. Since when it has
been live was not measured in this note: it is since the `#profile` section has existed on the
person's page. No data from another tenant: the reach was the whole tenant.

**What the fix does not undo**: whoever saw it, saw it. The trail is the same as #989's, below,
because the door is the same page and the same route: the `painel recusado` event marks each account
that opened the person without reach, and at that moment the profile was on the screen. For the
listing, the query on `api_access_reads` with `route = '/api/v1/people'` lists the tokens that read
it; which people were on the page of each read is not recorded (`target_id` only exists on the
detail route), and that is stated.

**It changes a screen in use without a new prototype**: the section disappears for whoever does not
reach, and the refusal that appears beside it is the one from the *Work* section, already approved.
No new element was designed.

### #992 — a person's changes and discussions go through the verdict (issue #989)

**What it delivers**: whoever the verdict refuses no longer sees, on the person's page and in
`GET /api/v1/people/:id`, the titles of their PRs and the issues they commented on. Identity and
provenance remain visible to the whole tenant. Whoever has reach sees the same as before.
Decision of the maintainer of 2026-09-27: PRs and discussions the person took part in are
**work**, and not identity.

**What was live, since v0.6.x (#430, 2026-08-18)**: the person's page has a section,
*Where this came from*, that sits **outside** the panel the verdict protects. It should have only
the provenance — where the person came from, with which identifier, since when —, but it also
carried two lists that are work:

- **Changes**: the titles of the PRs the person opened, reviewed and merged, and the commits;
- **Discussions they took part in**: the issues they commented on, with the title.

Both were loaded for **any authenticated account of the tenant**. Whoever the screen refused saw
the panel closed and, just below, the titles. The API repeated the exposure on purpose:
`GET /api/v1/people/:id` returned `changes` and `discussion_participation` to whoever the verdict
refused, *"because on the screen they are also outside"*. **There is no data from another tenant**:
the reach was the whole tenant, against what the maintainer decided on 2026-08-26 (023's FR-012:
the person themselves, the declared leadership, the scope and the administration).

Found by the security assessment of feature 069, part 2, as a side finding, and measured on
2026-09-26 with a probe: account refused with `{:nao, :sem_elo_declarado}`, PR title visible,
work section hidden.

**Why no test caught it**: there was a test, and it **required** the exposure
(`person_detail_test.exs`, *"discussões e mudanças continuam vindo para quem o veredito
RECUSA"*), and it only checked `is_map`, with no populated data: it had no way of seeing a title leak.

| Door | Before | After |
|---|---|---|
| screen `/people/:id` | both lists loaded and drawn for everyone | loaded only with the verdict (`se_pode`), and both blocks only appear with `@ve_o_trabalho?` |
| API `GET /api/v1/people/:id` | `changes` and `discussion_participation` always | `null` when `access.can_see_work` is `false`, like `work` |

061's contract (`specs/061-api-publica/contracts/api-v1-people.md`) and the OpenAPI schema were
amended in the same PR: both fields are `nullable`, with the reason written down.

**The evidence**: `test/the_band_web/trabalho_dentro_do_veredito_test.exs`, five tests, both
doors, with a PR and a discussion with unique titles. The refused account sees neither; the admin
sees both, and that is what proves the `refute` is not empty. **Injected defect**: `main`'s screen
in place of the fixed one fails 1 of 5 (*"a tela mostrou o PR a quem o veredito recusa"*); `main`'s
API fails 1 of 5 (`changes` is not `null`). Restored from the checked copies, all 5 pass.

#### What the fix does not undo: who may have seen it

It applies to #992 and to #946, which exposed on the same page and the same route.

**A title that has already been seen does not come back**, nor does the profile. What can be known
is **who saw it**, and both doors leave a trail:

1. **Every refused view generated the `painel recusado` event** in the application log, level
   `warning`, with `user_id`, `tenant_id`, `alvo_person_id` and the reason. On the screen and in the
   API, the event is emitted exactly in the case that exposed the titles. Search the production log
   for:

   ```text
   acesso: painel recusado
   ```

   Each line is an account that opened the page, or the route, of a person it could not see. If the
   person had collected PRs or discussions, the account saw the titles; if they had a stored
   profile, it saw the profile.

2. **In the API, each read granted by the token is in `api_access_reads`**, since v0.9.0. The
   query below lists the tokens that read `/people/:id`. Crossing the `target_id` with the log lines
   above, one knows which credentials received the titles:

   ```sql
   SELECT r.token_public_id,
          r.target_id           AS person_id,
          count(*)              AS leituras,
          min(r.occurred_at)    AS primeira,
          max(r.occurred_at)    AS ultima
   FROM api_access_reads r
   WHERE r.route = '/api/v1/people/:id'
   GROUP BY r.token_public_id, r.target_id
   ORDER BY ultima DESC;
   ```

**What is not known**: the retention of the production log was not measured. If it keeps less than
since 2026-08-18, the views from before the cutoff are left without a trail, and that is stated.

The searches run **in production**, and are an act of whoever operates: the `deploy-producao` agent
or the maintainer. No agent in this session accesses production.

## The MCP server (spec 062)

**What the person can now do**: connect an AI agent to The Band with the API token they already
issue at `/api-tokens`, and ask it about a team — who is in it, what each person has open, how long
the work waits for review and what is stopped —, receiving in each answer **the caveat in the same
object**: the composition, the window, the source, the rule with its version, the limitations and
the wrong interpretations, read from the knowledge base, and the collection date. The agent sees
exactly what the person who owns the token would see on the screen and in the API, and nothing more.

**It ships without a recorded acceptance**: see *The exception to the rule that only what is
accepted ships*, above.

The new surface: `POST /mcp`, in the router's `[:api, :api_autenticada]` pipeline, the same as
`/api/v1`. Documented for integrators in `docs/api/mcp.md`.

## The API contract for whoever the verdict refuses

**The question**: `GET /api/v1/people/:id` now returns `profile`, `changes` and
`discussion_participation` as `null` for a token without reach over the person, and
`GET /api/v1/people` no longer brings `competencies` of the people outside the reach. For whoever
integrates without reach, the shape of the response changes. Does that make the release MAJOR?

**Decision: no. It is a fix, and the release stays MINOR.** The reasons, in order of weight:

1. **What the response carried for whoever had no reach was the defect, and not a guarantee.**
   061's contract returned both fields to the refused party *"because on the screen they are also
   outside"*: it copied the screen's exposure, and the screen's exposure contradicted 023's FR-012,
   decided on 2026-08-26, which is what defines who sees a person's work. Semver protects what the
   product promises to whoever uses it; it does not protect access to data that the access rule
   already denied. Calling this MAJOR would be declaring the leak a feature;
2. **whoever has reach receives exactly the same response.** No field changes type, name or
   meaning for the legitimate use of the route;
3. **the signal was already in the response.** `access.can_see_work` already existed, and `work`
   was already `null` when it is `false`; `profile` and `competencies` could already be `null` (no
   profile generated). A client that reads the response as documented already handles `null` in
   those fields. What changes is that `changes` and `discussion_participation` now follow the same
   signal as `work`, and the note says **refusal**, not absence;
4. **the contract was amended in the same PR that changed the code**: 061's `api-v1-people.md` and
   the OpenAPI schema declare the fields `nullable`, with the reason (#946, #992). There is no silent
   divergence between what the documentation promises and what the route does.

**What is stated, because it is true even without being MAJOR**: an integrator who read `changes` or
`discussion_participation` with a token without reach, and did not handle `null`, **will break**
after the merge. That is an intended consequence: they were reading what they should not. If there
is a token in that situation, the query in *Who may have seen it* shows it, and the conversation with
whoever issued it is the same as the one about the exposure.

And, for completeness: the series is `0.x`. Under semver, before `1.0.0` the public API is not
stable, and not even a real break would force the jump to `1.0.0`. The decision above does **not**
rely on that: the release notes of this house apply the MAJOR, MINOR and PATCH table to `0.x` as if
it were stable (see `v0.9.2.md`), and it is by that yardstick that the change
is not MAJOR.

## After the merge

The order, and whose each step is. No agent in this session accesses production.

1. **the CD publishes and delivers**: merging the release PR into `main` triggers the workflow, which
   creates the `v0.10.0` tag, publishes `ghcr.io/the-band-solution/theband:v0.10.0` and calls the
   Dokploy webhook. Nobody builds, tags or publishes by hand;
2. **the version live**, checked against the source and not against `mix.exs`:

   ```bash
   curl -s "$PRODUCAO_URL/version"   # tem de responder 0.10.0
   ```

   While it answers `0.9.2`, the three fixes are **not live**, and nothing below starts;
3. **the `deploy-producao` agent** follows the delivery and checks health after it;
4. **the searches for who may have seen it**, in production, by `deploy-producao` or by the
   maintainer:
   - N5: the query of reads by token from a suspended tenant;
   - H2-R and #989: the `acesso: painel recusado` event in the log, and the `/people/:id` query on
     `api_access_reads`, crossed by `alvo_person_id`;
   - the **retention of the production log**, measured, because without it one does not know what
     the search reaches;
   - result recorded in this note, in *What was observed afterwards*, with rows or with "no
     rows", and never omitted;
5. **the `aceitacao-em-producao` agent** measures what is measurable without an account: `/version`
   and the anonymous side. `/mcp`, `/people/:id`, `/api-tokens` and `/teams/:id` are authenticated,
   and stay **not measurable**, never "accepted" (record of 2026-09-24);
6. **back-merge** from `main` to `development`, by merge commit (L92).
