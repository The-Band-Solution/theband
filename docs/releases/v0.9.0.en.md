## Why 0.9.0, and not 0.8.1 or 1.0.0

`mix.exs` says `0.8.0`, which is the version in production. Nothing is removed, no public field
changes meaning and no migration destroys data — so it is not MAJOR. It is not
PATCH because the behavior changes for users: seven routes that return 404 today
start answering. **MINOR: `0.8.0 → 0.9.0`.** There is no contract to break because there
was no contract: the screen that **generates** the token has been live since v0.8.0 without any
door to use it, and this release is the door.

## #936 came in — decided on 2026-09-23

[#936](https://github.com/The-Band-Solution/theband/pull/936) was **merged**, and this
release carries it. It fixes two **high** findings: no
successful read was recorded (`AccessEvents` only records refusals, and `last_used_at`
is an overwritten stamp — FR-024 of 045 points to the access record as the way
to notice aggregation, and it did not exist), and there was no rate limit at all.

The recommendation was that it come in, and the table below is what backed the recommendation. It stays
for the record of the decision — the left column is what the release **carries**:

| | with #936 — **what was done** | without #936 |
|---|---|---|
| rate limit | exists on the day the surface is born | **does not exist**, for an indefinite time |
| detecting abuse afterwards | `api_access_reads` records read by read | impossible: nothing is recorded |
| US5 of 061 (*Rate limit per token*, P2) | delivered | declared and not delivered |
| migration | one, **additive**: creates `api_access_reads`, deletes nothing, rollback loses no data | none |
| version | remains **0.9.0** | 0.9.0 |

**The reason is the coincidence of dates, not the size of the diff.** The risk of having no rate
limit only exists from the instant the routes answer — and it is that instant that
the release creates. Shipping without #936 opens the surface and postpones its control; since no
read is recorded, what was not contained before cannot be detected afterwards: no prevention and
no observation. The MCP spec ([062](../../specs/062-servidor-mcp/)) makes it worse by saying it
inherits "the limit of 061" — inheriting a nonexistent control is inheriting zero. Cost of including:
one additive migration. Cost of postponing: a second deploy window for a control that
should be born together with the door.

**The decision was taken on 2026-09-23: #936 came in.** The public API is born in production
**with** a rate limit and **with** a read record, and US5 of 061 ships delivered instead of
declared and absent.

### The window slides — corrected on 2026-09-23, after the deploy

The first version used a **fixed** window, and the limitation was declared in the PR: at the turn of the
minute, the counter reset and it was possible to issue **up to double** in a few seconds — 240
calls with a limit of 120.

It was corrected right after the release went live: the minute started being counted in ten-second
slices, and the count is the sum of those covering the last sixty. The burst at the turn drops
from a whole minute to ten seconds of imprecision, and the sum is **stricter** than the
declared window, never looser.

**This correction is NOT in v0.9.0.** It enters the next release — v0.9.0 went to production
with the fixed window, and that is said here instead of being silently overwritten.

### The number 120, and whose it is

The limit is **120 calls per minute per token**, and it lives in
`api.access.thresholds`, in the knowledge base — **not** in a module constant, because
a threshold in a constant changes in a diff and nobody notices.

**It is marked as a proposal.** It was chosen by whoever implemented it, and not measured against real
use — there is no real use: the API is born in this release. When there is a measurement, the number changes **in
one place only**.

## The exception, declared

**There is no `docs/sprints/NNN/aceitacao.md` for 061.** Checked on 2026-09-23: the
latest is the one from sprint 032, and none covers 061. Only an accepted deliverable ships; this release
ships without an acceptance record. The verdict per criterion —
SC-010, SC-015 and tenant isolation — **has not yet been gone through with evidence**.

**There was no independent review** of the API design or of the security assessment.
Four attempts by agent failed on 21 and 22 September 2026. The gap is
declared in every PR and **must not be marked as fulfilled** by any merge:
a merge is not a review. Correct classification: *review did not occur*.
