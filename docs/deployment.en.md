# Deployment and environment variables

How to get The Band running — local, CI and production — and what each variable does.

**State of this document**: written on 2026-08-11, from `config/runtime.exs`,
`compose.yaml`, `.github/workflows/ci.yml` and the 22 migrations that exist in the repository.

---

## 1. The variable that decides whether the application boots

`THE_BAND_MASTER_KEY` — the key that encrypts the credentials of the connected tools.

**The application refuses to boot without it**, and that holds for **all** environments. There is no
built-in development key: a key in the repository is a leaked key.

```
Defina THE_BAND_MASTER_KEY com 32 bytes em Base64:

    export THE_BAND_MASTER_KEY=$(mix the_band.gen_key)
```

The only fallback is in `config/runtime.exs`, and it applies **only** when
`config_env() == :test`: a fixed and avowedly public key, which encrypts only fixture
data in a database discarded at the end of the run.

```elixir
case {System.get_env("THE_BAND_MASTER_KEY"), config_env()} do
  {blank, :test} when blank in [nil, ""] -> Base.encode64(<<0::size(256)>>)
  {value, _} -> value
end
```

### Why `nil` and `""` are treated as the same thing

Because distinguishing them cost a red CI. A workflow that references
`secrets.THE_BAND_MASTER_KEY` **without the secret being registered** sets the variable as an
**empty string**, it does not leave it absent. The previous version only covered `{nil, :test}`, and the
absence of the secret turned off the fallback: `mix test` failed with nothing wrong with the
code.

**Referencing a secret that does not exist is worse than referencing none.** It is recorded
as [L13](sprints/licoes-aprendidas.md).

### If the key is lost

The credentials encrypted with it become **unreadable forever**. There is no recovery — that is the
point of encrypting. It happened in this project: the original key of the development database
no longer exists.

The path is clean, and it takes three steps:

```bash
export THE_BAND_MASTER_KEY=$(mix the_band.gen_key)   # 1. chave nova, guardada
mix phx.server                                        # 2. sobe
```

3. At `/tools`: **end observation** on the affected tool — which destroys the
   unreadable credential — and then **resume observation** with a new token, which is validated
   against the source before being stored.

**Nothing besides the credential is lost**: people, teams, issues and payloads are not
encrypted.

### Rotation, when the key needs to change without losing data

Cloak decrypts with **any** configured cipher and always encrypts with the one marked as
`:default`. The order matters:

```bash
export THE_BAND_PREVIOUS_MASTER_KEY=$THE_BAND_MASTER_KEY   # 1. a antiga passa a ser leitura
export THE_BAND_MASTER_KEY=$(mix the_band.gen_key)          # 2. a nova entra como default
mix the_band.rotate_key                                     # 3. recifra os registros
unset THE_BAND_PREVIOUS_MASTER_KEY                          # 4. só então remove a antiga
```

Changing the variable **without** step 3 leaves the old records unreadable. The old key only leaves
the environment after no record depends on it.

## 2. All the variables

| Variable | Where it is mandatory | Default | What it does |
|---|---|---|---|
| `THE_BAND_MASTER_KEY` | **dev, prod** (fallback only in test) | — | encrypts credentials; without it the application refuses to boot |
| `THE_BAND_PREVIOUS_MASTER_KEY` | during rotation | — | reading with the old key while the records are re-encrypted |
| `DATABASE_URL` | **prod** | `ecto://postgres:postgres@localhost/the_band_dev` in dev | connection to Postgres |
| `SECRET_KEY_BASE` | **prod** | generated in dev | signs sessions and cookies |
| `PHX_HOST` | **prod** | `example.com` ⚠ | public host; see the trap below |
| `PHX_SERVER` | **release** | — | without it the endpoint does **not** come up in a release |
| `PORT` | — | `4000` | HTTP port |
| `POOL_SIZE` | — | `10` | connections in the Ecto pool |
| `DNS_CLUSTER_QUERY` | — | — | node discovery for clustering |
| `MIX_TEST_PARTITION` | partitioned CI | — | test database suffix per partition |

**`PHX_HOST` has a trap.** Without it, the default in production is `example.com`, and the
application boots: the generated links point to a domain that is not yours, and nothing fails.
Always set it in production.

**`SOME_APP_SSL_KEY_PATH` and `SOME_APP_SSL_CERT_PATH` are not used.** They appear
**commented out** in `config/runtime.exs`, generated by Phoenix. A grep of the repository
finds them, and that is why they are declared here: so that nobody configures them expecting an
effect.

**`PHX_SERVER` only matters in a release.** `mix phx.server` brings up the endpoint on its
own; `bin/the_band start` does not, and the symptom is an application that is up and answers
no request at all.

## 3. Local development

```bash
docker compose up -d                                  # Postgres 17-alpine
export THE_BAND_MASTER_KEY=$(mix the_band.gen_key)
mix setup                                             # deps, banco, assets
mix phx.server                                        # localhost:4000
```

**The compose volume has real data.** This project's development database holds
4455 issues, 135 repositories and hundreds of preserved payloads, collected from the source.

```bash
docker compose down          # para os containers, PRESERVA o volume
docker compose down -v       # APAGA o volume — a coleta inteira se perde
```

`-v` gives no warning. Re-collecting requires a valid credential and a window of the source's quota.

### The knowledge base is read once, at boot

The 94 YAML artifacts in `priv/knowledge_base/` are loaded into ETS when the application
boots. **Changing YAML has no effect without restarting.**

This bites in a way that does not look like a bug. It happened in this project: a mapping
rule created **after** boot did not apply, and the work screen showed three
divergences that would vanish with a restart. Nobody suspects the screen — they suspect the
rule.

```bash
# depois de mexer em priv/knowledge_base/
# Ctrl-C duas vezes, e:
mix phx.server
```

In production: **a new mapping requires a restart**. Plan for it as part of the knowledge
deploy, and not as an operational detail.

## 4. Quality gates

All nine, in one command:

```bash
mix gates                  # na ordem do CI, abortando no primeiro que reprovar
mix gates --list           # os nomes
mix gates --from testes    # retoma de um gate
```

`mix gates` is their **only definition**: `ci.yml` calls the same task, and so there is
no second list to go stale.

**It provisions `.venv` on the first run, and that is not a convenience.** Without the venv, the
Python validator **does not validate the shape** of the YAML: it warns that it skipped, records the failure and
exits non-zero. Whoever reads the output with `| tail` sees the warning as an environment note and
concludes it passed — that is what happened ten times in a row, until CI failed six
mappings ([L23](sprints/licoes-aprendidas.md)).

**Never `| tail` on a gate.** Run it, check the exit code, and only then summarize.

### Running the whole workflow on your machine

```bash
brew install act
docker stop the_band_postgres    # o serviço do workflow publica a 5432
act -j quality-gates             # configuração em .actrc, versionada
docker start the_band_postgres
```

The `docker stop` is necessary: without freeing the port, `act` fails at *Set up job* with
`port is already allocated` — which looks like a workflow error and is a port conflict.

**`act -n` does not work on this workflow.** Version 0.2.89 has a `nil pointer dereference`
when inspecting service containers in dry-run mode. Run without `-n`.

## 5. Migrations

22 in total, and **none removes a column**. The round trip is part of the gate:

```bash
mix ecto.migrate
mix ecto.rollback --step 1
mix ecto.migrate
```

Every migration in this project carries a `@moduledoc` explaining **why** the shape is what it is —
including the deliberate absences. Two worth reading before adding a column:

| Migration | What it declares |
|---|---|
| `create_issue_promotions` | does **not** create `sro_user_stories.status`, even though the deriver prints that column. The classification is a situation, and a situation is derived |
| `create_decomposition_links` | has **no** acyclicity `check_constraint`: the axiom `sro.rule04` records that a database constraint does not catch a transitive cycle |

Without those paragraphs, the absence of a column the deriver prints looks like an oversight,
and the next person adds it.

## 6. Job queues

Oban, with **two** queues configured in `config/config.exs`:

```elixir
queues: [ingestion: 5, transformation: 5]
```

**Declaring a worker on a queue that does not exist leaves the job `available` forever.**
Oban only runs configured queues, and there is no error: the job simply never runs. It happened
in this project with a nonexistent `:sync` queue, and the symptom was a collection that "completed"
without collecting anything.

When adding a worker, use `ingestion` or `transformation` — or add the queue to the
configuration, with the reason written down.

## 7. Production

### Release

```bash
MIX_ENV=prod mix release
```

```bash
export THE_BAND_MASTER_KEY=...        # do cofre da infraestrutura
export SECRET_KEY_BASE=$(mix phx.gen.secret)
export DATABASE_URL=ecto://usuario:senha@host/banco
export PHX_HOST=seu.dominio
export PHX_SERVER=true                # sem ela o endpoint não sobe

bin/the_band eval "TheBand.Release.migrate"   # se houver módulo de release
bin/the_band start
```

### Deploy order, and why it is this one

1. **migrate** — the migrations do not remove columns, so the old version keeps
   working on the new schema;
2. **bring up the new application**;
3. **restart**, if the knowledge base changed — YAML is read at boot.

Step 3 is the one that gets forgotten. A deploy that changes a mapping and does not restart delivers
new code with old semantics, and the difference shows up as wrong data instead of an error.

### What needs to be in the vault, and not in the repository's environment

| Secret | Consequence of a leak |
|---|---|
| `THE_BAND_MASTER_KEY` | every credential of every tool of every tenant |
| `SECRET_KEY_BASE` | forgeable sessions |
| `DATABASE_URL` | direct access to the database |

**The master key never enters the repository**, and CI does not reference it — it uses the test
fallback, which is public by decision.

## 8. Known problems, and what each message means

| Message | Cause | What to do |
|---|---|---|
| `:missing_master_key` | variable absent or empty | `export THE_BAND_MASTER_KEY=$(mix the_band.gen_key)` |
| `:invalid_master_key` | it is not 32 bytes in Base64 | generate it with the task; `1234` will not do |
| `AES.GCM...` when decrypting | a different key from the one that encrypted | rotate, or redo the credential through end/resume |
| `port 4000 already in use` | a server is already up | `lsof -nP -iTCP:4000 -sTCP:LISTEN` |
| `port is already allocated` in `act` | local Postgres on 5432 | `docker stop the_band_postgres` |
| Oban job `available` forever | queue not configured | use `ingestion` or `transformation` |
| `[schema] jsonschema não instalado` | venv absent | `mix gates` provisions it; **the gate failed**, it did not just warn |
| the screen shows an unexpected classification | YAML changed without a restart | restart the application |
