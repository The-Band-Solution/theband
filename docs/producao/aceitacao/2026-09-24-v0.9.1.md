### C. API sem sessão: a recusa uniforme

O formato do token vem de `priv/knowledge_base/rules/api_access_thresholds.yaml` na v0.9.1:
`tb_api_<id_publico>_<segredo>`, com id de 6 bytes (8 caracteres base64url) e segredo de 32
bytes (43 caracteres). O Bearer inventado segue esse formato e tem marca de invenção:
`tb_api_ACEITE00_AAAA…A` (59 caracteres).

```bash
U="$PRODUCAO_URL/api/v1/teams"
curl -s -o $S/c1.b -w '%{http_code}\n' "$U"                                  # i   sem Authorization
curl -s -o $S/c2.b -w '%{http_code}\n' -H 'Authorization: Basic xyz' "$U"    # ii  malformado
curl -s -o $S/c3.b -w '%{http_code}\n' -H "Authorization: Bearer $FAKE" "$U" # iii Bearer plausível
curl -s -o $S/c4.b -w '%{http_code}\n' -H "Authorization: Bearer " "$U"      # iv  Bearer vazio
curl -s -o $S/c5.b -w '%{http_code}\n' -H "Authorization: $FAKE" "$U"        # v   token sem "Bearer"
for i in 1 2 3 4 5; do sed -E 's/"request_id":"[^"]*"/"request_id":"X"/' $S/c$i.b > $S/n$i.b; done
shasum -a 256 $S/n?.b | awk '{print $1}' | sort | uniq -c
```

### D. Método de escrita: a ordem entre 401 e 405

```bash
for M in POST PUT PATCH DELETE; do
  curl -s -o $S/d_$M.b -w "$M HTTP %{http_code}  " -X $M "$PRODUCAO_URL/api/v1/teams"; cat $S/d_$M.b; echo
done
curl -s -o $S/d.b -w "POST com Bearer inventado HTTP %{http_code}\n" -X POST -H "Authorization: Bearer $FAKE" "$PRODUCAO_URL/api/v1/teams"
curl -s -I -w "HEAD HTTP %{http_code}\n" "$PRODUCAO_URL/api/v1/teams"
```
```
POST   HTTP 401  {"error":{"code":"unauthorized","message":"The credential presented is not usable.","request_id":"GNhGm-LYG0E6SwEAAAWh"}}
PUT    HTTP 401  {"error":{"code":"unauthorized",…,"request_id":"GNhGm_lQ7hg6SwEAAAXB"}}
PATCH  HTTP 401  {"error":{"code":"unauthorized",…,"request_id":"GNhGnA3Ydh46SwEAAAXh"}}
DELETE HTTP 401  {"error":{"code":"unauthorized",…,"request_id":"GNhGnCJ6s0g6SwEAAAYB"}}
POST com Bearer inventado HTTP 401
HEAD   HTTP 401  (content-type: application/json)
```

**Ordem observada**: sem credencial válida, o 401 vem antes do 405. É assim por construção:
no roteador da v0.9.1, `scope "/api/v1"` faz `pipe_through [:api, :api_autenticada]`, e o
`match :*, …, :nao_permitido` só roda depois da autenticação.

**O que a spec promete**: não define a precedência. O SC-006 diz *"0 métodos além de `GET`
e `HEAD` respondem em `/api/v1`"*. O contrato `erro.md` diz 405 para *"qualquer método além
de `GET` e `HEAD`"*. O quickstart §7 mede o 405 **com** `Authorization: Bearer $TOKEN`.
Nenhum dos três pede 405 para quem chega sem credencial. Então a ordem observada não
contradiz a spec, e o "não responde" do SC-006 se cumpre para quem chega anônimo: nenhuma
escrita foi atendida. O código 405 em si só se mede com token válido.

## Achados

1. **Caminho inexistente sob `/api/v1` responde com a página HTML do site, e não com o
   formato único de erro.** Pode ser defeito de implementação (causa 2) ou lacuna da spec
   (causa 3). Quem decide é o PO.
   ```bash
   curl -s -o $S/nx.b -w "HTTP %{http_code} ct=%{content_type}\n" "$PRODUCAO_URL/api/v1/nao-existe"
   curl -s -o $S/nx2.b -w "HTTP %{http_code}\n" -X POST "$PRODUCAO_URL/api/v1/nao-existe"
   ```
   ```
   GET  /api/v1/nao-existe  HTTP 404 ct=text/html; charset=utf-8   <!DOCTYPE html>… <title>TheBand · The Band
   POST /api/v1/nao-existe  HTTP 404                               <!DOCTYPE html>…
   ```
   FR-020 diz *"um formato único para todos os códigos"*, e o contrato lista `404
   not_found` em JSON. Um cliente que escreveu "um tratador, não seis" (`erro.md`) recebe
   HTML e quebra no parse em vez de ler `error.code`. **O que quem integra veria**: um erro
   de JSON inválido, sem `request_id`, no lugar de `not_found`. O comentário do roteador
   recusa de propósito o curinga que daria 405 (*"a mentira inversa"*), mas nada no
   roteador nem nos testes de `test/the_band_web/api` cobre o caminho inexistente. A
   distinção 401/404 sem credencial não vaza nada: as 8 rotas estão publicadas na descrição
   OpenAPI anônima.

2. **Sem credencial, o 401 vem antes do 405** (item D). A spec não diz qual vem primeiro.
   O comportamento é defensável: não confirma nada a quem não se identificou. Vale deixar a
   ordem escrita no contrato `erro.md`, para que ninguém trate a ordem como defeito depois.

3. **O funcionamento do "Copy value" não se verifica em produção sem escrever lá.** Para
   ver o botão é preciso gerar um token. Pela regra da conferência, isso é um achado sobre o
   critério, e não uma autorização para gerar. Mesmo com conta de teste, esse item continua
   de fora, a menos que se decida outra fonte de evidência (por exemplo, conferir só o JS
   servido, como o item B faz).

4. **(local, fora de produção)** O ref `main` local deste checkout está parado (`mix.exs`
   `0.2.0`), enquanto `origin/main` está em `0.9.1`. Não afeta a produção. Só engana quem
   comparar versões contra `main` sem `origin/`.

Classificação: nada aqui é "a release não subiu" (causa 1). A versão no ar é a esperada, e
o estado do "Copy value" é o herdado e já registrado.
