# Runbook — The Band in production (Contabo + Dokploy)

Feature 050 · [spec](../../specs/050-em-producao/spec.md) ·
[pipeline contract](../../specs/050-em-producao/contracts/pipeline-de-release.md)

Written for ONE person to execute without this session open. The steps marked
**[MILESTONE — person]** are acts that only whoever administers can do; everything else is
either already in the repository or is the CD doing it on its own. **No secret appears in this
document, in the repository or in chat — ever.**

## §1 [MILESTONE — person] The VPS and Dokploy

1. Create the VPS at Contabo — 8 GB of RAM covers panel + app + Postgres at today's
   scale; Ubuntu LTS; your own SSH key (not a password).
2. Install Dokploy (official site: `curl -sSL https://dokploy.com/install.sh | sh`
   — check the script before running it, as with any curl-pipe).
3. Open the panel, create the administration account for the PANEL (not to be confused with the
   platform's accounts), and write down the address — with no own domain for now, the
   domain generated by Traefik will do (FR-013; HTTPS included).
4. **Dokploy's own updates and Contabo snapshots turned on** — Dokploy
   is infrastructure too (spec: whoever operates it is one person; the snapshot covers the
   panel and its config).

## §2 [MILESTONE — person] The secrets — the list is CLOSED (contract)

| Where | Key | Where it comes from |
|---|---|---|
| GitHub → Settings → Secrets → Actions | `DOKPLOY_WEBHOOK_URL` | the deploy webhook that §3 generates |
| Dokploy panel (app env) | `DATABASE_URL` | §4 generates it when creating the database |
| Dokploy panel | `SECRET_KEY_BASE` | `mix phx.gen.secret` locally, paste it directly |
| Dokploy panel | `THE_BAND_MASTER_KEY` | `mix the_band.gen_key` — a NEW production key, never the dev one |
| Dokploy panel | `PHX_HOST` | the host from §1.3 |
| Dokploy panel (registry) | `read:packages` credential | ONLY if the ghcr package is private |

Nothing beyond this. A key that leaks is ROTATED (the master key through §12, and not through `mix`,
which the release does not have), never "monitored".

## §3 [MILESTONE — person] The app in Dokploy

1. Create Application → **Docker Image** → `ghcr.io/the-band-solution/theband:latest`.
2. **Auto-deploy on push: OFF** (FR-015 — whoever deploys is the CD, after the
   gates; Dokploy only obeys the webhook).
3. Copy the app's **deploy webhook** → it is the value of `DOKPLOY_WEBHOOK_URL` (§2).
4. Internal port 4000; the domain from §1.3 pointing to it; automatic HTTPS.
5. Env vars from §2.

## §4 [MILESTONE — person] The database and the backup

1. Create Database → PostgreSQL 16 in Dokploy; the generated internal URL is the
   app's `DATABASE_URL` (§2).
2. **DAILY scheduled backup** in Dokploy to an S3-compatible destination (off the
   machine — FR-007/FR-014); a failure of the job shows up in the panel, and §6 says how to
   check it as a routine.
3. Contabo snapshot turned on (§1.4) — the second layer.

## §5 Rollback

Dokploy keeps the image history: redeploying the previous version means pointing the
app to `ghcr.io/...:vX.Y.(Z-1)` and redeploying — migrations are append-only by
house principle (data is never deleted), so the previous version comes up over the
new schema. A migration that breaks this is an ADR decision BEFORE the release, never
something discovered during the rollback.

## §6 The restore rehearsal — BEFORE real data (FR-008/SC-003)

The backup only exists after it has been restored once. The rehearsal:

1. Write down THREE numbers from production while it STILL has no real data (post-seed): people, issues,
   organizations — from `/people` and `/organizations`.
2. Download the most recent backup from the S3 destination (the job's `.sql`/`.dump` file).
3. Create an EMPTY database in Dokploy (`band_ensaio`), restore into it
   (`pg_restore`/`psql < dump`), point a SECOND temporary application in
   Dokploy to it (same image, the rehearsal's `DATABASE_URL`).
4. Check the three numbers ON THE SCREEN of the rehearsal instance — if they match, the rehearsal
   passed; write down the date and the numbers in `docs/releases/` alongside the release.
   **Since spec 071**: the roles are not part of the `pg_dump`. In the rehearsal cluster, create
   `the_band_owner` and `the_band_app` before restoring (§14.2), restore as `postgres`, and
   bring up the rehearsal instance with the owner's `DATABASE_MIGRATION_URL` and the `DATABASE_URL` of the role that
   serves. The deploy reapplies the grant. The rehearsal only passes if the check in §14.4, run
   against the rehearsal instance, says **"separação em vigor"** (separation in force).
5. Tear down the rehearsal instance and database.

If any step failed: the backup does NOT really exist — solve it before any
release with real data.

> **In a REAL restore, and not in the rehearsal, the last step is §10: end
> all sessions. It is mandatory** (feature 064, decision P5), and §10.1 says why. Repeat the rehearsal at every change in the backup design, and
at least once a month (SC-006: the routine runs for 7 days and the oldest one restores).

## §8 The first account — feature 052

The platform comes up with an empty database, and `seeds.exs` raises in production on
purpose: a known default password would be the open door that 045 exists to
close. Without this step, nobody gets in.

1. In the panel, in the application's environment tab, add to the ones that already exist:

   | variable | what |
   |---|---|
   | `THE_BAND_TENANT_NOME` | readable name of the organization |
   | `THE_BAND_TENANT_SLUG` | stable identifier — lowercase letters, numbers and hyphen |
   | `THE_BAND_ADMIN_EMAIL` | sign-in e-mail |
   | `THE_BAND_ADMIN_SENHA` | password chosen on the spot, at least 12 characters |
   | `THE_BAND_ADMIN_NOME` | optional — without it the person fills it in at `/profile` |

2. Deploy. In the container log, one of these four lines:

   | what appears | what it means |
   |---|---|
   | `primeira conta criada: <email>, admin de <slug>.` | it worked |
   | `já existe administrador — nada a criar.` | the installation already had an account |
   | `sem <VAR>, <VAR> — nenhuma conta criada.` | a variable is missing, and the line says which |
   | `primeira conta recusada: <campo> <motivo>.` | invalid value, and the line says which rule |

   **In all four cases the platform comes up.** Unlike `DATABASE_URL`, whose
   absence brings it down, here the lack does not prevent it: without a database, coming up would mean
   serving zero on every screen; without a first account, the platform is correct and
   merely empty.

3. Sign in through the sign-in screen with that e-mail and that password.

4. **REMOVE `THE_BAND_ADMIN_SENHA` from the panel.**

   While the variable exists, the first administrator's password is **readable
   by anyone with access to the panel**. That is the declared cost of the choice of
   environment variables, and not an oversight — an installation screen would carry the
   password from the keyboard to the hash with no intermediate stop, and it was discarded for
   simplicity.

   Removing it affects nothing: on the next boot the log will say `já existe
   administrador`. And changing the password through the interface after that holds forever
   — restarting does not overwrite it.

5. The following accounts are born at `/accounts`, with a temporary password generated by
   whoever administers. This step is only for the first one.

## §9 [MILESTONE — person] The own domain — feature 054

**The order is the part that matters.** Each inversion produces a different symptom, and
none of them names the cause. It is written in the order in which it needs to happen.

### Before anything: the repository ready

`THE_BAND_ORIGENS_EXTRAS` already needs to exist in the version that is in production.
Publishing the new name with a version that does not know the variable delivers an
address that answers 200 and is not interactive — the screens do not update, and there is no
visible error. It is P1 of 050, and it is the defect this feature exists not to
introduce.

Check before touching the DNS:

```bash
bash scripts/medir-enderecos.sh https://[redigido]
```

### 1. The DNS points — WITHOUT the intermediary in front

At the domain provider, **one** address record:

| Name | Points to | Note |
|---|---|---|
| `[redigido]` | the production IP | **with the intermediary turned off** — on Cloudflare, the **grey** cloud |

**Do not touch the apex or `www`.** `theband.dev` serves the **public site**, today
on GitHub Pages (`[redigido]` and siblings). Pointing it to production would take the
site down; adding it to the application in the panel would make the two services compete for the
same certificate.

*If you invert it*: whoever issues the certificate needs to prove it controls the name, and the
proof arrives as a request to the address itself. With the intermediary in front,
it may never arrive — and the symptom is a certificate that does not come out, without saying
why.

### 2. The name goes into the panel, and the certificate is issued

In the host's panel, on the application: add **`[redigido]`** — and only
that — pointing to the application port (`4000`), with HTTPS by Let's Encrypt.
Wait for the certificate.

> ⚠️ **On 2026-09-01 this step did NOT work, and the path was a different one.** What was
> measured: DNS resolving straight to the origin, route existing (`Host: [redigido]`
> → 301 to the right host), application answering 200 behind the wrong
> certificate, ACME challenge path open (404 from the handler, not a redirect),
> no CAA on the domain, and the domain's `Certificate` field already set to `Let's
> Encrypt`. Even so, the origin kept serving `CN=TRAEFIK DEFAULT CERT`.
>
> **The cause was not diagnosed** — the Traefik log was never read. It is
> recorded as what it is: a step that failed without explanation, and not a step that
> works. Whoever resumes starts at `dokploy-traefik` → Logs, filtering for `acme`.
>
> The path used instead is in **§9-B**, below.

**`.dev` has no plan B.** The TLD is on the browsers' HSTS preload
list: without a valid certificate, the browser refuses before any
request goes out. There is no "open it insecure and the person proceeds" — there is
unreachable. **Do not announce the name before this step finishes.**

Check:

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://[redigido]/sign-in   # 200
curl -s -o /dev/null -D - http://[redigido]/sign-in | head -2         # 301 → https
```

### 3. The two origins are declared — BEFORE changing `PHX_HOST`

In the panel, in the application's variables:

```
THE_BAND_ORIGENS_EXTRAS=https://[redigido]
PHX_HOST=[redigido]
```

**In that order, and in the same deploy.** `THE_BAND_ORIGENS_EXTRAS` is *where
people arrive from*; `PHX_HOST` is *the address the platform writes into links*.
Changing only the second leaves the old address without a live connection — which is the same
defect, in the opposite direction.

Leave the continuous measurement running during the deploy, to prove SC-004:

```bash
while true; do
  printf '%s %s\n' "$(date +%H:%M:%S)" \
    "$(curl -s -o /dev/null -w '%{http_code}' --max-time 10 \
       https://[redigido]/sign-in)"
  sleep 5
done
```

### 4. The intermediary comes in — and encryption goes all the way to the application

Only now turn on the proxy (**orange** cloud), with:

- **encryption mode**: the one that also encrypts **between the intermediary and the application** and
  validates the certificate. On Cloudflare, `Full (strict)`;
- **live connections (WebSockets)**: on.

*If you choose the mode that encrypts only up to the intermediary*: the application requires encryption
(`force_ssl` in `config/prod.exs`), the intermediary answers that it already encrypted, and
a **redirect loop** is born — the page never loads, and the error does not
name the cause.

*If live connections are turned off*: HTTP answers 200 and no screen
updates. The same symptom as P1, with a different origin — that is why step 5 exists
even when step 2 passed.

### 5. The check that decides: the socket, at both addresses

```bash
bash scripts/medir-enderecos.sh https://[redigido]
bash scripts/medir-enderecos.sh https://[redigido]
```

**Both have to pass.** A `200` on HTTP is evidence of nothing here: the
defect of this feature produces exactly a 200 with the socket refused (L85). The
script prints the reading of the codes — `403` is an origin refusal, `400` is `curl`'s
incomplete handshake with the origin **accepted**.

### §9-B — The alternative path: the intermediary's origin certificate

**This is how production came up on 2026-09-01**, after Let's Encrypt did not
issue. It holds as a permanent alternative, and not only as a patch — with a
difference that needs to be written down: **renewal stops being automatic**.

1. **Cloudflare → SSL/TLS → Origin Server → Create Certificate**. Hostnames
   `*.theband.dev` and `theband.dev` — the one-level wildcard covers `[redigido]`. Default
   validity of 15 years;
2. **the private key appears only once.** It goes from the Cloudflare panel straight
   to Dokploy's: never through chat, never through a repository file (FR-011);
3. **Dokploy → Certificates** → custom certificate, pasting certificate and
   key. Then, **Domains → `[redigido]`** → `Certificate` field pointing
   to it;
4. **Cloudflare → DNS** → record `[redigido]` → **Proxied** (orange);
5. **Cloudflare → SSL/TLS → Overview** → mode **`Full (strict)`**. In the new
   interface: *Configure* → *Custom SSL/TLS* → `Full (strict)`;
6. **Network → WebSockets: ON**.

**Whoever presents the certificate to the browser becomes Cloudflare**, with its
Universal SSL — measured on 2026-09-01: `CN=theband.dev`, issuer
`Google Trust Services`. The origin certificate encrypts and **authenticates** the
Cloudflare↔server leg.

> **Do not use `Full` without `(strict)`.** It accepts any certificate at the origin,
> including self-signed: the leg is encrypted and **not authenticated**, and an
> intermediary there goes unnoticed. With the origin certificate installed,
> `Full (strict)` works on the first try — there is no reason for the weak mode.

**What this path leaves open**: renewal. The Let's
Encrypt certificate renewed by itself; this one expires in 15 years and nobody will be reminded. When
Let's Encrypt works again, switch the domain's `Certificate` back and
stay on `Full (strict)`.

### 6. The pending item is closed

With both addresses measured, mark **P1 of 050** as closed in
`specs/050-em-producao/pendencias.md`, with the date and what replaced it.

## §10 Sessions — what a restore does to them, and how to end all of them

Feature 064 (US2, T015 and T016). Since T013, each sign-in opens a row in
`user_sessions`, and the database keeps **only the digest** of the token. The token that opens the session
lives only in the browser cookie.

### §10.1 What a restore does to sessions

Restoring a backup brings back the session rows **from the instant of the copy**. There are three cases:

| the session was… | after restoring | why |
|---|---|---|
| opened **after** the copy | **drops**, and the person signs in again | the row does not exist in the restored database |
| opened **before** the copy, and still within the 7 days | **stays valid** | the row came back unchanged |
| **ended between the copy and the disaster** | **BECOMES VALID AGAIN** | the row came back without the `ended_at` |

**The third case is the one that surprises, and it is the dangerous one.** The sessions ended in that
interval include those ended **for security reasons**: someone who left a shared
computer, a password changed on suspicion, a disabled account. The restore
reopens them without anyone having asked.

**The same holds for the password.** A password changed after the copy goes back to being the
old one, because the `password_hash` and the epoch come back too.

That is why the step below is **mandatory** after every restore, and not
recommended.

### §10.2 End all sessions

> **This ends EVERYONE's session, in ALL organizations, including that of
> whoever runs the command.** Everyone needs to sign in again. There is no way to
> choose who stays.

In the app container, through Dokploy (*Advanced → Terminal*, or `docker exec` into the
application container). **There are two commands, and which one to use depends on whether the application is up**
(#1050):

| the application | command | why |
|---|---|---|
| **up** (the normal case) | `/app/bin/the_band rpc 'IO.puts(TheBand.Release.girar_sessoes())'` | runs **inside the node that serves**, and the notice brings down the open screens |
| **stopped**, for example right after restoring, before bringing it up | `/app/bin/the_band eval 'TheBand.Release.encerrar_todas_as_sessoes()'` | starts another VM just for this; there is no open screen to bring down |

Through `eval` with the application up, the sessions are ended in the database, but a screen that is already open
keeps answering until it reconnects. That is the #1042 defect on the incident path, and it is why
`rpc` came in.

The output says **how many** sessions it ended, and only the number:

```
7 sessão(ões) encerrada(s), e as telas abertas foram avisadas. Todas as pessoas precisam entrar de novo.
```

The command writes `ended_at` on every open session and **deletes nothing**. The rows
go away by themselves 90 days later, through retention (T020). Running it twice does no harm: the
second ends zero.

**When to run it:**

| situation | mandatory? |
|---|---|
| **after restoring a backup** | **yes** (§10.1, decision P5) |
| suspicion that the `SECRET_KEY_BASE` leaked | recommended. **Changing the key (§2) is what protects**: every cookie signed with the old one stops being valid. The key alone does not open a session, because the database does not have the raw token. Ending records the drop in `ended_at` |
| the secret scan (`mix the_band.varre_segredos`, FR-010) found a session token | yes |
| suspicion of a stolen session, without knowing whose | yes |
| a single account | **do not use this.** Disabling the account (`/accounts`) ends its sessions, and re-enabling does not bring them back |

**How to check that it worked:** open the platform in a browser that was signed in.
It needs to land on `/sign-in`.

### §10.3 What this does not do

- **Through `eval`, it does not bring down an already connected LiveView** (finding S14, later #1042 and #1050).
  Through `rpc`, it does: the open screen rechecks the session and lands on `/sign-in`.
- **It does not change the key.** If the suspicion is about the `SECRET_KEY_BASE`, changing it is a
  separate step, in §2.

## §11 The stopped queue — when `/syncs` says the queue is not moving

Issue #801. The `/syncs` screen warns when no Oban job has completed in the last **15 minutes**.
The rule is in `docs/producao/saude-da-fila.md`: `Cron` schedules work every 5 minutes, and
three cycles with nothing completed is a stopped queue, not slowness. The same rule makes the
container healthcheck become `unhealthy` and `/health` answer `503`.

### §11.1 What this means

- **The runs marked `running` are not advancing.** The record says `running` because
  nobody ended it, and the queue is not running the work.
- **Nothing that has already been collected is lost.** Each page is written after it is processed, with the
  checkpoint. When the queue comes back, reconciliation **ends** the run that stayed `running`
  without advancing (§11.2, step 5), and the tool's **next** collection restarts from the written
  checkpoint, without re-collecting what already came in.
- **Sync and Reprocess stay disabled** while it lasts, because each click would create one more
  `running` record that would not move either.

### §11.2 What to do

1. **Check from the outside:**

   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' "$PRODUCAO_URL/health"   # 503 = parada
   ```

2. **Before restarting, check whether a genuinely long collection is in progress.** The collection of a
   large organization takes hours, and the warning may appear if several run at the same time. On the
   `/syncs` screen, a run whose last-progress line shows recent progress **is moving**:
   wait instead of restarting. Restarting brings down the collections that are running.
3. **Restart the application container** in Dokploy: *Applications → the_band → **Restart***. **Do not
   use Redeploy:** it pulls the image again and may change version, and a stopped queue is not
   solved by changing version. Restarting is what solved it on 2026-09-04: 0 jobs completed in 20
   minutes before, 122 in 3 minutes after.
4. **Check that it came back:** `/health` answers `200`, and the `/syncs` screen shows *Job queue
   moving* again within a minute, because it rechecks every 60 seconds.
5. **The runs that stayed `running` without advancing** are ended by reconciliation
   (`ReconcileStuckSyncs`), which runs again with the queue. There is no need to end them by hand.

**Do not change `oban_jobs` through SQL to "unstick" the queue.** Changing `state` by hand was needed
once, on 2026-09-04, in development, and in a queue stopped for the wrong cause it hides the
problem instead of solving it. If restarting does not solve it, the cause is something else: the connection to the database, or
the Oban supervisor giving up. Investigate before touching the table.

### §11.3 What this procedure does not know

**Why the queue stopped.** The checker detects, and does not explain. The cause of the 2026-09-04 stop
was never found.


## §12 Rotate the master key — issue #1052

The master key (`THE_BAND_MASTER_KEY`) encrypts **all** fields of
`TheBand.Rotacao.campos_cifrados/0`: the tools' credentials and the AI provider's
credential. Before #1052, rotation re-encrypted only the former, and the provider's became unreadable.

The release does not have `mix`, and therefore `mix the_band.rotate_key` does not exist in production. The path
is this one, through Dokploy:

1. **Generate the new key** outside the server (`mix the_band.gen_key`, on a machine with the
   repository). It does not pass through chat, commit or log.
2. **In the Dokploy panel**, copy the current value of `THE_BAND_MASTER_KEY` into
   `THE_BAND_PREVIOUS_MASTER_KEY`, and put the new key in `THE_BAND_MASTER_KEY`.
3. **Redeploy** (*Redeploy*), so that the `Vault` comes up with both keys.
4. **Re-encrypt**, in the container terminal, inside the node that serves:

   ```bash
   /app/bin/the_band rpc 'IO.puts(TheBand.Release.rotacionar_chave())'
   ```

   The output says how many records it re-encrypted per table, and never a value. If it says
   **"NADA FOI GRAVADO"** (nothing was written), there is a record unreadable with both keys. Stop and check step 2,
   **without** removing the previous key.
5. **Only after re-encrypting**, remove `THE_BAND_PREVIOUS_MASTER_KEY` from the panel and redeploy.
   Keeping the old key published keeps alive the key that was meant to be retired.

**How to check:** after step 5, open a connected tool and the AI
credential screen. Both need to keep working: collection continues, and the profile round does not report an
unreadable credential.

## §13 The platform operator — spec 070

The platform operator suspends and reactivates organizations, at `/platform`. They are not an account of
any organization, and **no screen grants, resets or revokes the role** (FR-001): only the three
commands below, run in the container terminal, through Dokploy. Whoever runs the command already has the
database, and the command is the **recorded** path for that.

`quem executa` (who executes) is **declared**, and not authenticated: the command records what was written there. The proof of
who ran it is access to Dokploy, outside the application.

### §13.1 Before the first grant: the server clock

The second factor is TOTP, with 30-second codes. A server whose clock is off by more than 30
seconds refuses **every** code, and [redigido] refusals in a row lock the second factor until the reset
(T11 of `seguranca-totp.md`). On the server:

```bash
timedatectl
```

The output needs to say `System clock synchronized: yes`. If it says `no`, fix NTP before
granting. Record the check in the release note, with the date. If the clock was not checked,
write "not measured", and not "ok".

### §13.2 Grant the role

**The person who will become operator runs the command themselves**, or receives the code **by voice**. Never
by chat, e-mail, issue, commit or screenshot (A17): the code opens the password setup of the
most powerful account on the platform.

```bash
/app/bin/the_band eval 'TheBand.Release.conceder_operador("<e-mail>", "<nome>", "<quem executa>")'
```

The output prints the setup code **once**, with a validity of 30 minutes. It is not kept
anywhere besides the digest in the database: if lost, another one is issued with §13.5.

Granting again to someone who already had the role brings back nothing from before: the password, the second factor, the
recovery codes and the old sessions are deleted.

### §13.3 Enrollment, in three steps

At `https://<endereço>/platform/setup`:

1. **The password.** The e-mail, the setup code and the new password, from 12 to 128 characters, twice.
   The code is valid once.
2. **The authenticator.** The screen shows the **setup key** in text and the
   `otpauth://` address. There is no QR code, by decision of 2026-10-01. In the authenticator app, choose
   "enter key" and type the key; then confirm with a code from the app. **The key appears
   only on this page**: if the page is closed before confirmation, a new code is needed
   (§13.5). This step expires in 10 minutes.
3. **The recovery codes.** The screen shows ten codes, **once**. Keep them away from the
   computer and from the authenticator's phone. Tick the box and finish. This step also expires in 10
   minutes.

**Until the third step, sign-in is refused**, even with the right password and code.

### §13.4 Sign in

At `https://<endereço>/platform/sign-in`, with the e-mail, the password and the code from the app. Without the
app, use a recovery code in the same field. Each code is valid for **one** sign-in.

Every refusal says the same sentence, whatever the wrong field, including during the wait after
several attempts. The session lasts 8 hours, and drops after 30 minutes without use.

### §13.5 Losing the phone, or locking the second factor

**A lost phone means a reset through the command, even if there are still recovery codes** (T9 of
`seguranca-totp.md`). The recovery code gives one sign-in, but does not revoke the lost device, and
the secret on it remains valid until the reset.

The reset is the same for whoever got [redigido] codes wrong in a row (the second factor locks) and for whoever
lost the password:

```bash
/app/bin/the_band eval 'TheBand.Release.reiniciar_credencial_do_operador("<e-mail>", "<quem executa>")'
```

The reset deletes the password, the second factor and the recovery codes, ends the sessions and prints
a new setup code, **once**, with the same rule as §13.2 for handing it over. Enrollment
restarts from §13.3.

### §13.6 Revoke the role

```bash
/app/bin/the_band eval 'TheBand.Release.revogar_operador("<e-mail>", "<quem executa>", "<nota>")'
```

Revocation ends the operator's sessions in the same transaction, and an act in flight is refused. It is
final: to give the role back, it is granted again (§13.2).

## §14 The database roles — spec 071 (#1131)

The application **migrates** with a role that owns the schema and **serves** with another, without ownership and only with
read and write of rows. Without this, whoever executed SQL through the application could turn off the
guards that live in the database: the append-only triggers, the `CHECK`s and the FKs.

- **The target** (decided on 2026-10-02): `the_band_owner`, owner and **not** superuser, only to
  migrate; `the_band_app`, without ownership, to serve. `postgres` stays only for administration and
  backup.
- **No password passes through chat, issue, commit or log.** Generate and keep it yourself, in the Dokploy
  panel.

### §14.1 Measure before changing

In Dokploy's Postgres terminal, as `postgres`, on the application's database:

```sql
SELECT rolname, rolsuper FROM pg_roles WHERE rolname = current_user;          -- quem é você
SELECT pg_get_userbyid(datdba) FROM pg_database WHERE datname = current_database();
SELECT tableowner, count(*) FROM pg_tables WHERE schemaname = 'public' GROUP BY 1;
```

Write down, without a password, in issue #1131:
- which role today's `DATABASE_URL` uses;
- whether it is a superuser;
- who owns the tables;
- whether Dokploy's scheduled backup uses `--no-acl` or `--no-owner`.

### §14.2 Create the roles and transfer ownership

Generate two **hexadecimal-only** passwords, which do not break the URL:

```bash
openssl rand -hex 32
```

And, as `postgres`, on the application's database, with the passwords in place of `<…>`:

```sql
CREATE ROLE the_band_owner LOGIN NOSUPERUSER NOCREATEROLE NOCREATEDB PASSWORD '<senha do dono>';
CREATE ROLE the_band_app   LOGIN NOSUPERUSER NOCREATEROLE NOCREATEDB NOREPLICATION NOBYPASSRLS
                            PASSWORD '<senha de quem serve>';
REASSIGN OWNED BY <o dono de hoje, de §14.1> TO the_band_owner;   -- só nesta base
ALTER DATABASE <a base> OWNER TO the_band_owner;
```

**Never** `GRANT the_band_owner TO the_band_app`, nor the database with `OWNER the_band_app`. Either
of the two gives back to the serving role the power to turn off the guards, and the check says
`membro_do_dono` or `dono_de_objeto`.

### §14.3 Change the credentials in the panel, BEFORE the deploy

In the Dokploy app:
- **the credential that migrates is a file, and not a variable** (#1140). In *Advanced → Mounts*, create a
  **File Mount** with the path `/run/secrets/database_migration_url` and the content
  `ecto://the_band_owner:<senha do dono>@<host>/<base>`, on a single line;
- `DATABASE_URL`: `ecto://the_band_app:<senha de quem serve>@<host>/<base>`;
- if `DATABASE_MIGRATION_URL` exists in the panel, **delete it**. [redigido] It is still accepted for the transition, with a warning, and the
  file wins if both exist.

Redeploy. The container starts as root only to read the file:
- it proves that `band` cannot open it, and **does not come up** if it can;
- it migrates, and grants the privileges to the serving role;
- it drops to `band` before the server.

The process that serves has no capability at all and does not read the file. Without the first, the deploy follows the three states of FR-008:
- if the serving role is still owner, it migrates as today, and says "NÃO em vigor" (NOT in force);
- if it is not owner and there is no pending migration, it comes up;
- if it is not owner and there is a pending one, it **does not come up**.

```

### §14.5 Undo a migration

DATABASE_URL="$(cat /run/secrets/database_migration_url)" /app/bin/the_band eval 'TheBand.Release.rollback(TheBand.Repo, <versão>)'
```
