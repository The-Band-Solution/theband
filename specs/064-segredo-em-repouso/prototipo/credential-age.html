Credential Age Request

The two screens that administer a third-party credential, Connected tools and AI provider, show how long each credential has been in use. Three months after one is saved, the screen asks for a replacement and says how long it has been, in months and with the date. It asks; it never blocks. Collection and generation keep working with the old credential.

Every state must read without colour. Toggle to check.

"Today" on this page is 2026-10-03. Organisations, labels, logins, last four characters and dates are example; none comes from a real workspace. The three-month rule is real: TheBand.Credenciais.Idade.limite_em_meses/0.

The marks

within 3 months registered less than 3 months ago
replace · 4 months in use past 3 months: the request
age unknown no date, never counted as within
inferred from the last check the date is derived, not recorded

The date beside the mark is the one the platform recorded when the credential was saved. The mark is computed from that date and the three-month rule, on every page load. The three states are rendered one by one; there is no default branch.

screen 1 · connected tools

Tool credentials: one age per credential, the request above the list

A tool can hold several credentials. Replacing a token adds a new row and leaves the old one where it is; nothing on this screen rewrites a secret. So the age belongs to each row, and the request names the row by its label.

Who sees the request, and where

  • Administrator: every tool's requests on /tools, and the key's on /ai.
  • Someone who answers for an organisation (organisation scope): on /tools only the tools of the organisations granted, so only their requests. A request on another organisation's tool is not hinted at, not even as a count. On /ai, the key's request, because the key is one for the whole workspace (decision of 2026-08-28).
  • Anyone else: redirected as today; sees no age and no request.
  • No part of a secret is in the request: tools are named by label, the key as “this key”. The last four characters stay where they already are, in the credential row.
decisions and open questions

Decisions and open questions

The D items are the design proposed for approval. The Q items need the maintainer's answer; each has the options and the recommendation.

D1 · proposed 2026-10-03The age is a date plus a span, never a span alone

Always the recorded date (2026-05-28). Below one month, the span in days (“29 days ago”, “today”). From one month, whole calendar months, rounded down (“4 months”). The within state also shows the date the request starts (“replacement asked from 2026-12-04”), which is the recorded date plus limite_em_meses/0.

D2 · proposed 2026-10-03Three marks with three shapes

within 3 months thin outline, quiet, not a success badge. replace · 4 months in use amber double border with “!”. age unknown dashed, italic, with whose absence it is. Distinct in greyscale.

D3 · proposed 2026-10-03The request is a notice where the credential is administered

On /tools under the “Credentials” heading of the tool, one notice per overdue active credential, named by label. On /ai inside “Key in use”. It says how long, the date, the rule, that nothing stops, how to replace (including revoking at the source) and who can. It contains no part of the secret.

D4 · proposed 2026-10-03No new action, nothing disabled, no snooze

The request points at the actions that exist (“replace the token”, the key form). No button is disabled by age, no collection or generation checks it, and the request cannot be dismissed: it goes when the credential is replaced or deactivated.

D5 · proposed 2026-10-03On tools, replacing is two steps, and the request follows them

Right after a new token is added the old one is still active and overdue, so the request changes to “The new token is in. ‘service account’ is still active.” and asks to deactivate or remove it (1c).

D6 · proposed 2026-10-03On the key, the previous date is shown after a replacement

The flash says which date was replaced and that the count starts again. “Key in use” gains a “previous key” line with both dates and the span (2e), from previous_secret_set_at and secret_set_at.

D7 · proposed 2026-10-03An inferred date is marked as derived

A key saved before replacement dates were recorded uses the last check as its date (contract, em_uso_desde/1). The screen says so with the hatched mark (2c), because the migration deliberately left it unfilled to keep that visible.

D8 · proposed 2026-10-03The environment key is age unknown, never within

Rendered as age unknown with the platform named as the one lacking the date, inside the existing environment warning (2d). Security assessment, finding 3.

D9 · proposed 2026-10-03The tools column “validated at” becomes “registered”

For a tool credential the two instants are the same (the row never changes its secret). The column shows the date and the mark instead of the raw timestamp. On /ai “checked against the provider at” stays, because there the two dates differ; “key registered” is added.

Q1 · openAn inactive tool credential past three months
  • (a) the same request as an active one;
  • (b) no request; the row shows its date and mark, and a quiet line under the table: “‘read-only backup’ is inactive and was registered N months ago. Its secret is still stored; remove it if it is no longer needed.”;
  • (c) nothing but the date and mark on the row.

Recommendation: (b). The secret is still at rest, which is what spec 064 is about, but “replace” is the wrong action for a credential nobody uses. Removing is the right one.

Q2 · openDoes age unknown ask for anything?
  • (a) the mark only;
  • (b) the mark plus a dashed notice saying the age cannot be told and how to get a dated one: replace it, or for the environment key, ask whoever runs the server or save one for the organisation (drawn in 1d and 2d).

Recommendation: (b). FR-019 forbids counting it as within. A mark alone tells the reader that something is unknown but not what to do about it. The environment key is the one with the widest reach.

Q3 · openA mark beyond the request's own screen
  • (a) only on the screen that administers the credential, as FR-017 says;
  • (b) also a replace mark on the Connected tools / AI provider tab, so either screen points at the other (drawn in 2a and on the phone);
  • (c) (b) plus a mark in the main navigation or an e-mail. That is new scope and needs its own spec.

Recommendation: (b). It costs one assign per screen and covers the case of someone who only opens Connected tools. SC-009 (“nothing goes unnoticed”) is fully met only with (c); register it in the backlog and do not do it here.

Q4 · openSaving the same key again: say so?
  • (a) the flash says “It is the key already registered, so it still counts from 2026-05-28.” (2f), found by comparing secret_set_at before and after the save;
  • (b) the usual flash; the card shows the unchanged date.

Recommendation: (a), provided the security agent agrees. Without it, someone who changed only the model reads “saved” and thinks the request was met. Finding 5 of the assessment says knowing whether the key is the same gives nothing to someone who can already overwrite it, and the dates on the card already reveal it.
