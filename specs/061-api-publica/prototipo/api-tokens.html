API tokens

A token lets a program read this organisation through the public API. A token carries no permission of its own: it sees exactly what its owner account sees, and that reach is read again on every call — so it grows and shrinks with the account's links, with nobody touching the integration.

what this screen is for Generate a token, hand the value over once, and revoke it when the integration ends. The value is shown a single time, at creation — the platform keeps a one-way hash and the last four characters, and there is no screen, export or endpoint that shows it again. If it was not copied, the way forward is to revoke this one and create another.

ana.vieira@the-band-solution.example reaches, right now: her own person record · team IA · projects ConectaFapes and Valida — the two projects that team IA is linked to. No granted scope on this account — everything above is derived from her current links.

This is today's reach, not the token's. If she leaves team IA, the next call returns less, and nothing on this screen changes. If her account is ever disabled, every call with this token is refused. That is the trade this platform took, in the open: no second model of access, and a reach that ages with the person instead of in the token.

“No expiration” is offered, and it is a choice with a cost. 90 days is the suggested term (api.access.token_lifetime); choosing no expiration is explicit, never the easy default. A token with no end leaves circulation only by deliberate revocation. No job ends it, and nothing announces that it exists — this screen is the only surface, and nobody opens an admin screen on a Tuesday without a reason. Two things limit the damage, and both still hold: the reach is the owner account's, read again on every call, and a disabled account has every call refused. An endless token belonging to someone who left already opens nothing. reverted on 23 Sep 2026 · the rule previously read “a maximum you can opt out of is not a maximum”

The platform stores the label, a one-way hash of the secret, the last four characters, who created it, when, and the expiry. It does not store the value, and there is no column it could be recovered from.

the gap this list used to declare, and no longer has

Until 23 Sep 2026 this said: what each integration read is not recorded. It is now — one row per accepted call, with the credential, the route, the target and the instant. The body of the response is not kept: the record says who read what, never what was read. Two consequences worth naming. The row below opens a usage panel instead of a ninth column — the eight of R2.1 are the QA's ruler. And the record is kept indefinitely (api.access.access_log_retention, decided 23 Sep 2026): nothing prunes it, so it can reconstruct, with no time limit, that one person consulted another person's panel.

The usage panel

opens on the row — not a ninth column

Clicking a row opens this. It answers “what has this credential been reading?” — the question the list refused until 23 Sep 2026. It stays out of the table because the eight columns of R2.1 are what the QA checks one by one, and because this is a panel someone opens to investigate, not something to scan across six rows.

what this panel does not show, and why

Not what was read. The record keeps the route and the target, never the body of the response — keeping it would make a second copy of the data, with the same sensitivity and without the verdict in front of it.

Not a refused call. Refusals are already in the internal log, with the reason. This panel is about access that was granted, which is what left no trace at all before.

why this panel exists

Four calls that each respect the verdict can, together, answer a question none of them would answer alone. The verdict cannot see accumulation; this panel can. It is the control the platform accepted when it accepted that risk — and until this screen existed, the control was a table nobody looked at.

and this panel is itself a record about people

It shows that one person's credential read another person's panel, when, and how often. The record is kept indefinitely — decided 23 Sep 2026, in api.access.access_log_retention, after 90 days was proposed and turned down. Nothing prunes it.

Who may open this panel is the same door as the rest of the screen: require_admin. That is not a small thing to leave implicit, so it is written here.

Reach is recomputed on every call and on every load of this screen — it is never written into the token. Six rows, no page cut: when a tenant passes a screenful of tokens this list gets paging, and says so here.

screen 3 · revoking, with the label named

Revoking the wrong token stops a third party's integration — and that third party is not in the room. So the confirmation names the label, and says what is calling with it right now.

Revoke “planilha do RH”?

••••••••••••••••Lq08 owner ana.vieira@the-band-solution.example · created 28 Aug 2026 last accepted call 14 minutes ago

Something is calling with this token today. If you did not expect that, this is the moment to find out what — and if you did, whatever it is stops working the second you confirm.

what it doesThe next call with this token is refused — immediately, with no cache and no delay between this click and the refusal. The row stays on the list, marked revoked, with the instant and your name.

what it does not doIt does not delete anything, it does not touch the other tokens of this account, and it cannot be undone. There is no reactivate: a revoked credential is a credential someone decided to stop trusting, and a pause would not be that decision. The way back is to create another token and hand it to whoever integrates.

what the client seesThe same 401 as a token that never existed — same code, same message. The caller is not told that the credential was revoked, because telling them confirms it once existed. Whoever operates this platform finds the real reason in the internal log, by the request id.

The clause that earns this field is suspected leak — it is the one case where the next act changes: rotate everything that account reaches, not just replace the integration. The list is closed so the answer to “how many revocations were suspected leaks this quarter?” is a count and not a reading of free text; the note sits beside it for what a list cannot hold.

Until 23 Sep 2026 revocation recorded only who and when — and that was an omission, not a decision: nobody had been asked. A revocation with no reason is a decision nobody reconstructs in six months.

screen 4 · what this screen refuses, and why

Each of these is something a person could reasonably come here expecting. A control that is missing without a word makes people conclude the platform cannot do it — so the screen says it, in the place where they would look.

“Let me generate my own token”

expected: a button on the profile screen

Only administration generates tokens. This screen lives behind the same door as accounts and access scopes. Self-service is a later decision, and it is a decision about who may hand out credentials — not a missing button.

“Let me rename it, or push the expiry out”

expected: an edit pencil on the row

A token is not edited after it is created. Extending the life of a live credential grants time without generating anything anyone had to hand over again. The label is fixed at creation for the same reason the mask is: the row has to keep meaning what it meant.

“Show me what this integration read” now answered

this card used to be a refusal — it is not one any more

It said “only when, never what”. That stopped being true on 23 Sep 2026: every accepted call is now recorded — which credential, which route, which target, when. The body of the response is not recorded: the log says who read what, never what was read. The row gains a usage panel, below — not a ninth column, because the eight of R2.1 are the ruler the QA checks one by one.

“Put it back — I revoked the wrong one”

expected: a reactivate button on the revoked row

There is no reactivate, anywhere on this screen. Revocation is definitive; create another token and hand it over. The revoked row stays visible so the mistake is legible rather than erased.

“Give this token access to one more team”

expected: a scope editor on the row

A token has no scope of its own. Access is granted to the account, on the access-scopes screen, and the token reads it at every call. A scope stored on the token would be a second answer about access — and it would age in the pocket of whoever left.

“Show me the value again — I lost it”

expected: a reveal on the row

Nothing stored can produce it. The platform kept a one-way hash, not an encrypted copy, because it never needs the value back — it only ever needs to check one. Revoke and create another.

And the account that is not an administrator

refusedAPI tokens are managed by administrators. Your account does not carry the administrator mark in The Band Solution, so this screen is not open to you. Ask someone who administers this organisation to generate a token and hand it over. — the refusal names the reason and the way forward; it is not a blank page and not a redirect that leaves someone guessing.

decisions and open questions

Decisions taken in this prototype

  1. D1The state chip carries the provenance of the state. Active and expired are amber hatched — they are read against the clock, at this instant, and there is no state column in the database. Revoked is grey filled with a declared mark beside it — a person did it, and the row carries the instant and the author. The screen's own grammar does the teaching: the only state anybody declared looks declared.
  2. D2The mask is sixteen bullets and the last four characters, fixed width, so it never hints at the length of the value. Two tokens of the same account are told apart by the label and by those four characters, and by nothing else. The house helper for tool credentials masks with four bullets; reusing it here would contradict this screen — the token mask is its own.
  3. D3Reach is shown on the row, in two lines, split by origin and never summed: what is derived from the account's current links (person record, teams, projects) and what was granted to it. Where either is empty the cell writes the absence and whose it is — "sees nothing today — no person declared for this account" — with what the API does about it: accepted call, empty collection.
  4. D4The reach preview lives inside the create form, under the owner select. The consequence people get bitten by — the reach changes when the person changes teams — has to be visible while generating, not when a third party's dashboard empties out. It is one paragraph, and it links onward instead of becoming a second grants screen on this page.
  5. D5The clear value is a panel, not a modal, with the copy action, the instruction to put it in a secret manager, and the sentence that it will not come back written as what it does not do. The panel is the only place the value exists, and the list row beneath it already shows the mask — so the difference between "now" and "from now on" is visible in one glance.
  6. D6The value is annotated in three parts — public prefix, public id, secret — because all three are public knowledge except the last, and because it explains, at the only moment someone is looking, why a leaked token is findable by a scanner and why checking one never searches the database by its hash.
  7. D7A reload shows one quiet line, not a second chance. "Created 2 minutes ago, shown once, cannot be shown again — if it was not copied, revoke it and create another." The line names the recovery path, since the mistake it addresses is exactly someone looking for the value.
  8. D8The revocation confirmation names the label in the title and in the button, and carries the fact that actually stops a wrong revocation: when this token was last accepted. "Last accepted call 14 minutes ago" is what tells someone they are about to break something live. No typing of the label is asked — see Q3.
  9. D9An account that cannot sign in shows as two marks on one row — active (the record) and calls refused (the account behind it) — side by side, neither summarising the other. A row that said only "active" would be the screen affirming what the API denies.
  10. D10The refusals get a section of their own, each written as what someone would come here expecting. Six of them, including the declared gap about what an integration read. A missing control with no word next to it reads as a platform that cannot do the thing.

The six questions, answered on 23 Sep 2026

All six were put to the maintainer. Four had already been answered by the code without passing through her — those are confirmed below. Two were genuinely open, and one of the answers reverses a declared rule.

#questionanswer
Q1May a token be created with no expiration? declared yes — reverses the rule. The form offers 7 / 30 / 90 and no expiration. The consequence is written into api.access.token_lifetime: such a token leaves circulation only by deliberate revocation, and nothing announces that it exists.
Q2Which prefix does a token carry? already in the code tb_api_, in api.access.token_prefix.
Q3Should revocation require typing the label? already in the code no. The confirmation names the label in title and button, and shows the last accepted call — which stops a wrong revocation better than typing does.
Q4Does revoking record a reason? declared yes — four clauses plus a free note. Until now it recorded only who and when, and that was omission, not decision.
Q5Does the expiry warning ship in this slice? already in the code yes — the list reads token_expiry_warning.
Q6Does anything warn the owner before a token expires? postponed nothing warns anyone, and that is the state this screen must say out loud. Measured on 23 Sep 2026: this platform sends no e-mail at all. No dependency, no mailer module, no SMTP variable. So the answer first given — e-mail to the creator, 14 days out — was not an adjustment to this screen but a feature of its own: a provider, a credential, and an answer for what happens when delivery fails. Decided on 23 Sep 2026: postponed. The three changes above ship without it. What remains true meanwhile: token_expiry_warning marks the row 14 days out, and only someone who opens this screen sees it. Nothing reaches anyone who does not come looking — written here so it is a known gap and not a surprise.
+Where does API usage appear? (not one of the six — it came from the access record that shipped in v0.9.0) declared a panel on the row, not a ninth column. R2.1 keeps its eight.
what these answers oblige, before any code

Three of them change this screen. The house rule is that a screen change goes back to the prototype, and the ruler in section 3 of PROMPT.md has 60 items the QA checks one by one.

This republication keeps the same address — a new address would be a new prototype, and a new prototype needs a new approval. The three were approved on 23 Sep 2026, and the e-mail of Q6 was postponed in the same breath.

Names the knowledge base needs before the code

  • api.access.thresholds — the rule that holds every number this screen shows: api.access.token_lifetime (90 days, applied), api.access.token_idle_expiry (30 days without use, declared and not applied in this slice — and the rule says which is which), api.access.token_expiry_warning (14 days, and see Q5).
  • api.access.token_prefix — the public prefix (see Q2). It is printed on this screen, pasted into a scanner's pattern, and must not live as a literal in two places.
  • api.access.token_state — the vocabulary of the state column: active, revoked, expired, each with how it is read and whether a person declared it. The screen shows a fourth line that is not a token state — calls refused · owner account disabled — and it needs its own name so the row and the API agree on the words.
  • the words of the two absences, so the screen and the API say the same thing: never used (no accepted call yet) and no expiration (no end declared) — never a blank, never a zero, and never the creation date standing in for a use.
