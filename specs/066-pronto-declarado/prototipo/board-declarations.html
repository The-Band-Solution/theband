example — event types and counts come from the base

When an issue sits on more than one board — 13% of them do — the criterion that applies is the one from the board most recently linked to the project. Linking the new board last is already the gesture that says which one is current, so the platform reads that instead of asking twice.

If two boards were linked at the very same instant — which batch association does — the platform does not pick one. It names the tie and leaves the decision, because picking silently would be choosing where nobody would look.

Where evaluation happens

declared by this organisation067 · new

The platform never marks an item accepted (sro.rule03). What the organisation can say is which event of its own process is the evaluation — here, the client moving a card out of Homologation. Two steps: choose the stage where evaluation happens, then say what each exit from it means. Acceptance is derived at read time from the transitions each item actually made, always with the criterion, the instant and the actor beside it. Nothing here is proposed — recommending would be choosing (042).

decisions and open questions

Decisions taken in this prototype

  1. D1The two new cards sit right after Start criterion, in the order 042 → 066 → 067, each with its own heading and one question. Nothing else on the screen moves. A question-shaped heading in the house voice already on this screen ("What each iteration field means", "Where the deadline comes from").
  2. D2Proposal is amber hatched; active is info solid; no decision is dashed; revoked is grey solid. A proposal is derived from recognised vocabulary — the house mark for derived is amber hatch, so no new hue and no new form. The row for In Progress shows a proposal at rest; the row for Done shows an active rule and the proposal it came from.
  3. D3The five destinations are radios with the ontology id and one line saying what each asserts, and the list carries a dashed box Not offered here: accepted / not accepted citing sro.rule03 and linking to the evaluation card. The Desaprovado row carries the same pointer, because that is where a person would look for "not accepted".
  4. D4Revoke is shown as a mark on the record: the Homologation row keeps its earlier, revoked completed rule with author, instant and the one-line reason. The QA checks that revoking produces this row, never an empty cell.
  5. D5The evaluation card is two steps on one card — chips for the stage, a table for the exits — rather than two cards, because the exits have no meaning without the stage. Every observed exit is listed with its count; stages with no recorded exit are one collapsed row, so that a first occurrence has a place to land.
  6. D6Zero is written as a count — "0 · collected · up to 9 Sep" — and the Desaprovado row says why it is zero. Coverage is a fixed box under the table, on every screen that carries a count from 067.
  7. D7The third count, "no declared evaluation", refuses an item number in this prototype and lists the moves instead. The data measured is moves, not items; inventing an item count from 459 − 10 would sum two different populations. The implementation counts items.
  8. D8The item detail shows three statement cards side by side with their marks, plus a stage-period table with one row per pass and the source of each period; the person panel shows the same three, then coverage, then the two disagreement numbers. Where a figure was not measured today the tile says so instead of carrying an example number against a real person.
  9. D9Authors and instants of declarations are a fictitious administrator marked example — no declaration has been made yet, and the prototype does not attribute one to a real person.
  10. D10Unchanged cards appear as quiet stubs ("unchanged — as on the screen of 14 Sep 2026") to keep the order verifiable without redrawing what the QA compares to today's screen.
