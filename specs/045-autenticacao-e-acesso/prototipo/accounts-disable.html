Accounts

everything here is declared by the administration the GitHub login comes from collection 6 accounts · 4 can sign in today · 1 disabled · 1 has no password

Who signs in to this organisation, which GitHub account belongs to whom, and how someone's access is removed. There is no self-registration: an account is created here, and it is disabled here. example data marks the rows invented for this prototype — the development database on 10 Sep holds 3 accounts (2 with a password set, 1 with none, 0 disabled, 0 linked to a collected person), and every state below needs a row to be designed against.

Two screens on one page, separated by the band below. /accounts has no tabs, and this prototype does not invent any: screen 2 is the sign-in page seen from the other side, and it is here because the refusal it shows is part of this design. Everything is visible on load — the forms are open as examples, and nothing needs a click to be read.

screen 1 · accounts
what this screen is, and the finding it exists to close Before this design, the shutdown was implicit: whoever administered reset the password and did not hand the temporary over. The account of someone who had left then read temporary pending — the same words as an account created yesterday — and the routine act for the second one (reset the password) brought the first one back. The state of a shutdown was indistinguishable from the state of someone who had just joined the organisation.

Three things follow from that, and this screen is built on them: the account's state and the credential's state are two facts, so they are two columns; every act says what it does and what it does not do, in place, because the act that looked like a shutdown was not one; and nothing is erased — a disablement is an episode with an author, a date and a reason, and bringing the account back closes the episode instead of deleting it.

Removing someone's access

three acts · only one of them removes access

Someone left the organisation. These are the three acts this screen offers, side by side, with what each one does and what it does not do. Read this before acting: the act that reads like a shutdown is not the one that shuts anyone out.

Disable account

what it doesThe account stops signing in — by password today, and by API token when tokens exist. The open session drops at the next action. The row stays, with who disabled it, when, and why.

what it does not doDoes not delete anything. Does not remove the person from the roster, from any team, or from any measure. Does not change the password.

Reset password

what it doesIssues a new temporary password, shown once, and drops the open sessions. It is how someone who forgot their password gets back in.

what it does not doThis is not a shutdown. The account stays able to sign in, and the next reset — a routine act — hands it back. Not handing the temporary over is a habit, not a control.

Revoke GitHub link

what it doesThe account stops being that observed person: their own dashboard closes, and signing in by GitHub username stops working. The history of the link stays.

what it does not doDoes not remove access. Signing in by e-mail does not need the link, and the organisation's screens keep opening. Measured on 9 Sep.

why this panel is on the screen and not only in a document

The written procedure exists — docs/producao/desligar-alguem.md — and it exists because the act that worked was not written anywhere. A procedure that lives only in the documentation is exactly what this finding proved does not work: whoever administers does what the interface offers. So the interface says it, at the point of acting, and the document keeps the long version.

Disable an account

shown open, as the form appears after “Disable…” on Rafael Duarte's row

Disabled, not deleted. The row stays, and so does everything this person did.

what happens when you confirm

  • The account stops signing in — by password now, and by API token when tokens exist.
  • The open session drops at the next action, not seven days from now.
  • The record keeps who, when, why and this note, and it stays after any reactivation.
  • The password is not changed, the GitHub link is not revoked, and the scopes are not removed — they are kept and inert, so that bringing the account back restores exactly what was there.
  • The roster, the measures and this person's history do not change. Disabling an account changes who signs in, not what happened.

The same form with Suspected compromise chosen second state, shown so the checklist is on the page

disabling closes the door — these are the things it does not close

  • The open session — closed by this act, at the next action. Nothing else to do.
  • The password — unchanged, and you do not know who else knows it. While the account is disabled it opens nothing; reset it after any reactivation, never before.
  • API tokens — the platform has none yet. When it does (spec 061), disabling has to close them too, and until then this line is a promise and not a control.
  • What was read before now — nothing here is retroactive. What the person saw, they know.
  • The access record — what this account did, from the sign-in log. It starts on 9 Sep, when the platform began recording access events; before that date there is nothing, and the screen says so rather than showing an empty list.

Reactivate an account

the more sensitive of the two acts, and the one with the thinner record today

Disabling closes a door; reactivating opens one. It asks for the same author and the same reason, and it does not erase the disablement — it closes the episode, and both halves stay side by side on the row.

Reactivate Rafael Duarte — disabled 9 Sep 14:20 by Paulo Junior, left the organisation

what happens when you confirm

  • The account signs in again, with the credential it already had — password set · 14 Aug.
  • The scopes it had are live again: 1 organisation scope, granted 14 Aug by Paulo Junior. Nothing new is granted.
  • The episode closes with your name, this instant and this reason. The disablement above it stays exactly as it was.
  • Reactivating does not hand the password back. If the shutdown was done the old way — a reset whose temporary was never delivered — the password is still that undelivered temporary, and a fresh reset comes after this act.

What disabling does not touch

written on the screen, because the opposite is what people assume
the person, in the organisation's data Everything this person did stays: the roster, the team memberships, the work items, the demonstrated profile, every measure over any period. Disabling an account is a statement about signing in, not about the past. Someone who worked here in July still counts in July.
the account, on this screen The row stays, the link stays, the scopes stay and go inert, the credential stays as it was. Nothing is deleted, ever. The one thing that changes is the answer to “can this person sign in?”, and it changes with an author, an instant and a reason attached.
and one claim this screen cannot make on its own

“4 can sign in today”, at the top, is true while the organisation itself is active. A suspended organisation should sign nobody in — and tenants.status exists, accepts "suspended" and is read nowhere (measured 9 Sep, finding H3 part A). Until that is closed, the number above is about accounts and not about the door. Where that belongs on a screen is open question 14.

screen 2 · what the disabled person sees
what this screen is The sign-in page, from the other side, on the day after being disabled. It is here because the refusal has a rule of its own and the rule is easy to break by being helpful: the door never names the state of the account. Whoever did not get in must not learn from the answer whether the address exists, whether the password was the wrong one, or whether the account was disabled — that is enumeration, and it is what an attacker asks the door for.

The two statements

the door says one thing; the record keeps another
what the door says “Invalid credentials.” — byte for byte the same sentence a wrong password gets, and the same one an address that belongs to nobody gets. One sentence, built in one place, so it cannot drift apart into three.
what the record keeps sign-in refused · reason: account_disabled · user … · tenant … — the internal reason, in the access log, where reconstructing an incident needs it. The distinction the door refuses to make is made here, for the people who are entitled to it.

This is the same shape as everywhere else in this product: two statements side by side, and neither one pretending to be the other. What changes is who is allowed to read which.

what the person is not told, and who has to tell them

Nothing on this page says “your account was disabled”, and nothing should. The person finds out from a human being — which is why the disable form asks for a note, and why the reason is written down: somebody will have to answer “what happened?” and the answer should not be reconstructed from memory.

Decisions and open questions

10 Sep 2026

The code for this screen is already in production, shipped in v0.7.0 with the delivery refused. This prototype is not here to ratify what exists — it says what should exist, and the difference between the two is work. The table at the end names every difference.

  1. The reason is a closed list and a note. decided 10 sep Five clauses — left_the_organisation, access_no_longer_needed, duplicate_account, suspected_compromise, other — plus a free note. Why both: the clause is what the platform reads — “suspected compromise” changes what the screen shows next and is the one question an incident asks by count — and free text alone cannot be counted or routed. The note is what the person writes, and a clause alone repeats identically for forty people without saying who decided or on what basis. This house has precedent on both sides: the membership mistake demands written text, the concept promotion uses declared vocabulary. Here the two do different jobs, so both are present.
  2. The note is required for suspected_compromise and other, optional for the rest. decided 10 sep Required everywhere produces “asdf”, which is worse than absence because it looks like a record. other has no meaning at all without the note; suspected_compromise is the one whose next reader has to act. Where it is omitted, the record says no note — absence written, never a blank.
  3. Reactivating asks for an author and a reason, and it does not erase the disablement. decided 10 sep Four clauses: returned_to_the_organisation, disabled_by_mistake, investigation_closed_no_compromise (offered only against a compromise disablement), other. Reactivating is the more sensitive of the two acts — one adds a person to the set of people who can read the organisation — and today it is the one with the thinner record. A disablement is an episode: opened with author, instant and reason; closed with author, instant and reason. The account's state is derived from “is there an open episode?”, and the row shows both halves.
  4. Two columns, not one cell with precedence. decided 10 sep Account and Sign-in credential are two facts and get two columns. The screen in production puts desativada first inside the credential cell, which is precedence rather than separation: the credential fact disappears when the account is disabled, and it is exactly the fact you need on the day someone asks for the account back. One cell for two facts is the shape that made a shutdown read like a first day.
  5. The two temporaries are told apart in words. decided 10 sep temporary · from creation · never signed in against temporary · from a reset · last signed in 2 Sep. Separating the account column solves half the finding; this solves the other half. The two look identical today and ask for opposite acts — hand this one over, do not hand that one over — and both facts are already in the database (password_set_at, logged_in_at, must_change_password).
  6. A refused action is shown refused, never hidden. decided 10 sep Reset password on a disabled account keeps its place, inert, with the reason beside it and the correct order named: reactivate first, and reactivating does not hand the password back. Disable on your own row does the same, and it names the domain's refusal — :nao_pode_desativar_a_si — before it can be triggered. A button that vanishes is the mute absence this house refuses; and here it is worse than mute, because whoever looks for it concludes the platform cannot do it.
  7. The row carries the history. decided 10 sep Who disabled, when, why, with the note; who reactivated, when, why. Plus last signed in, which is what says whether a live session was cut. An account that was never disabled says no disablement recorded — written, not blank. The precedent is ScopeGrant: revocation is a mark with authorship, never a delete.
  8. The written procedure is on the screen. decided 10 sep Three act cards — Disable account, Reset password, Revoke GitHub link — each with what it does and what it does not do, above the table, always visible. docs/producao/desligar-alguem.md exists precisely because the act that worked was written nowhere; a procedure that lives only in a document is what this finding already proved fails, because whoever administers does what the interface offers.
  9. Disabling touches nothing else. decided 10 sep The password is not changed, the GitHub link is not revoked, the scopes are not removed — they are kept and inert, and the row says so. Joining any of them into one act is the error FR-012f already separated, and it would make reactivation guess at what to restore. The roster, the measures and the person's history do not move: this is a statement about signing in, not about the past.
  10. Disabled accounts stay in the same table, sorted last, never filtered out by default. decided 10 sep An account you cannot see is an account you cannot audit, and a second screen for “former accounts” is where the record goes to be forgotten. The filter exists and starts on all; the count is in the header.
  11. Marks: grey filled for disabled, clay hatched for mistake, plain words for active. decided 10 sep No new hue — the decision of 8 Sep found none free in this palette, and it still holds. Grey-filled is this house's mark for ended, and the record stays, which is what a correct disablement is; clay is gravity and error, which a disablement by mistake is; amber stays with the pending temporary, where it already lives. Active gets no badge at all: it is the common case, and a badge every row carries stops being a signal.

Open, and each one is the maintainer's to settle. Written with the options and this role's recommendation; the Product Owner takes them.

  1. Where the reason vocabulary is declared. open Nothing may be on the screen that the base does not declare (constitution, principle IV), and these nine clauses are declared vocabulary. (a) a rule file beside team.dashboard.thresholds, which is already a screen decision living in the knowledge base with provider: platform; (b) outside priv/knowledge_base/, because that base is the SEON network about observed engineering data and an account's lifecycle is platform administration. Recommended: (a) — the precedent exists, the validator already gates it, and “declared, versioned, reviewable” is the property that matters. If (b), it needs the same three properties somewhere else, not none.
  2. Whether a disablement can name a successor. open The example note says “handover to Marina done”, in free text. (a) leave it in the note; (b) an optional field pointing at another account, so “who took this over” is answerable by query. Recommended: (a) for now — (b) is a second relationship to keep true, and nobody has yet asked the question it answers.
  3. Where a suspended organisation appears. open tenants.status exists and nothing reads it, so the header's “4 can sign in today” is a claim about accounts and not about the door. (a) a banner on this screen when the organisation is not active; (b) its own screen, since it is a statement about the organisation and this screen is about people; (c) remove the column, if suspending an organisation was never the intent. Recommended: (a) plus (c) decided elsewhere — this screen must not claim someone can sign in when the organisation is closed, and a column that looks like a control and is not is worse than no column.
  4. How much history the row shows before it needs a door. open Four episodes read well; a five-year-old account with a dozen would push the table apart. (a) show them all, always; (b) show the open episode plus the last closed one, and a link to the rest; (c) a separate access-record screen per account. Recommended: (b), with the count always written — “2 earlier disablements” — so that what is not shown is still stated.

Where the screen shipped in v0.7.0 differs from this prototype — not implementation detail, and not adjustments to adopt. The rule of this house is that the implemented screen is exactly the approved screen; these are the changes the code has to make.
