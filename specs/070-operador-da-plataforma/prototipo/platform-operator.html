Platform Operator Screens

Five screens for the person who runs the platform: sign in with a second factor, set the password from a one-time code, enrol the authenticator, list the organisations, and suspend or reactivate one. The operator sees each organisation's name, slug and state, and nothing an organisation owns.

Every state must read without colour. Toggle to check.

All names, slugs, e-mails, dates, secrets and codes on this page are example. None comes from a real organisation or a real operator.

screen 1 · sign in

Sign in with password and code in one form

One form, three fields. There is no half-signed-in state between the password and the code. Any failure gives the same sentence, whichever field was wrong, and so does the wait after repeated failures.

screen 2 · set the password

Set the password with the one-time setup code

The setup code is printed once by the release command that grants the role or resets the credential. It works once and lasts 30 minutes. It is typed into the form and never travels in the address.

GET /platform/setupat rest
The Bandplatform operation

Step 1 of 3. Set your password. Step 2 adds your authenticator, and step 3 asks you to store the recovery codes. You cannot sign in until all three are done.

Setting the password signs out every open operator session and replaces any authenticator enrolled before.

Two refusals, never shown together; both are here only to be read. The first covers unknown email, wrong code, expired code, used code, no grant and the wait. The second can only appear after the code checked out (the contract rolls the code back), so it reveals nothing new.

Suspend Northwind Studio

Reason — required

What suspending does, at once and in one step

  • Every person in Northwind Studio is signed out, on every device.
  • Every API token of Northwind Studio is revoked.
  • Nobody in it can sign in, and no collection or background job runs for it.
  • Its data stays as it is. Nothing is deleted.
  • Reactivating later does not bring sessions or tokens back: each person signs in again, and each token is issued again.

Reactivate Acme Labs

Reason — required

What reactivating does, and what it does not

  • People in Acme Labs can sign in again, each one from the start.
  • No session comes back. Any session recorded while it was suspended is ended too.
  • No API token comes back. Each one must be issued again by the organisation.
  • Collection resumes on its normal schedule; reactivating does not start one.
  • The suspension above stays on the record; this closes it with your name, this moment and this reason.

The last block is how Legacy Works reads: the date is when the migration recorded the episode, not when the database was edited, and the author's absence is written, not left blank.

If the operator's session or grant ended between opening the page and submitting, the act is refused inside the transaction, the operator cookie is dropped, and the answer is the same 404 as below.

Not a screen: whoever is not an operator

An anonymous visitor, or an admin of any organisation, who opens any /platform/* address other than sign-in and setup gets the platform's ordinary 404 page: the same status, the same headers and the same body as /platform/a-path-that-does-not-exist. No redirect to sign-in, no “permission denied”, nothing that confirms the area exists. A slug that does not exist gets the same page.

The operator's own cookie opens nothing outside /platform: on /people it is treated as no session at all (redirect to /sign-in), and on the API and MCP it gets 401.

Decisions and open questions

decided 2026-10-01 · maintainer · already in the spec Separate operator, own cookie, screens by controller

FR-011 as amended (T005). So the real screens have no live updates and no inline script; every refusal is a re-rendered page. This prototype uses a small script only for the greyscale toggle.

decided 2026-10-01 · maintainer · already in the spec Second factor is required (FR-016), and the reason lists are closed (data-model §5)

The four suspend reasons and four reactivate reasons on screen 5 are the approved list, with the note required for Suspected compromise and Other, and Investigation closed — no compromise found offered only when the open suspension's reason is Suspected compromise.

decided 2026-10-01 · maintainer · D1–D5 approvedThe design decisions
  • D1 One refusal sentence per form, and no field marked. “In a moment” covers the wait without being a second message.
  • D2 “Shown once” comes before the setup key and the recovery codes; the refused states say they do not come back.
  • D3 Only the act that fits the state is offered; the other is absent, not disabled.
  • D4 Each episode is one block with two halves, and the missing half is written.
  • D5 A line above the organisation list says what the operator does not see.
decided 2026-10-01 · maintainer · Q1 (a)No QR code on the enrolment screen

The setup key as text and the otpauth:// address to copy. No new dependency.

decided 2026-10-01 · maintainer · Q2 (a)Confirm by typing the organisation's slug

For both suspending and reactivating, with the consequences listed above the field. The field is confirm_slug; a mismatch is refused with “The confirmation did not match” and nothing changes. The controller checks it before calling suspender/3 or reativar/3, whose contracts do not change.

decided 2026-10-01 · maintainer · Q3 (b)The operator must confirm the recovery codes were stored

A third step: a required box and one more POST, /platform/setup/recovery-codes. The authenticator and the codes become valid only when this step finishes. Abandoning it leaves the operator without sign-in until a new setup code, the same price as abandoning step 2. An unticked box is refused and does not use up the step; the codes are not shown again.

decided 2026-10-01 · maintainer · Q4 (b)No session or token counts in the history

They stay in the access log. The history shows who, when, why and the note, at both ends of each episode.

New names for the knowledge base

No new measure. Every reason label on screen 5 comes from platform.tenant_suspension (task T014), including not_recorded for the migration case. The sentences on these screens are interface copy in the controllers, not vocabulary of the base.
