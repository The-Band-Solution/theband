    Aceitação em produção: v0.9.1 (feature 061, lado anônimo), 2026-09-24¶

    Versão no ar: 0.9.1 (de /version) · Esperada: tag v0.9.1, e mix.exs de origin/main = 0.9.1 Endereço: https://app.theband.dev Autenticado: não. Decisão da pessoa mantenedora (2026-09-24): por enquanto não haverá PRODUCAO_TESTE_EMAIL/PRODUCAO_TESTE_SENHA. Nenhum token foi criado e nada foi escrito.

    Esta é a segunda execução. A primeira parou por falta de PRODUCAO_URL e deixou escrito o critério de "satisfeito" de A a F, que é o usado aqui sem mudança. A primeira execução não deixou relatório no repositório.

    As três versões batem: /version = 0.9.1, a tag v0.9.1 tem mix.exs 0.9.1, e origin/main tem mix.exs 0.9.1. O mix.exs de development diz 0.10.0: é a próxima release (commit e65c515), e não uma divergência de produção. A descrição OpenAPI servida também diz info.version = 0.9.1.

    Todos os comandos abaixo supõem set -a; . ./.env >/dev/null 2>&1; set +a e S=<scratchpad>.

    O que foi medido¶

    item critério (escrito antes de medir) medido veredito
    A /version responde 200, texto puro, corpo 0.9.1 200, text/plain, bytes 30 2e 39 2e 31 = 0.9.1 satisfeito
    B nenhum ouvinte de the_band:copy nos JS servidos (estado herdado da v0.8.0; #941 não publicado) 0 ocorrências nos 2 assets; controle positivo: LiveSocket aparece 4 vezes no mesmo arquivo satisfeito (bate com a nota)
    C 401, corpo {"error":{"code":"unauthorized",…}}, corpos idênticos exceto request_id 5 variantes de recusa, todas 401 JSON; depois de trocar o request_id por uma constante, os 5 têm o mesmo sha256; os 5 request_id são distintos satisfeito para a recusa anônima (a parte de FR-020/SC-003 que se mede sem conta)
    C' a mesma recusa em todas as rotas de FR-021 as 8 rotas da descrição OpenAPI devolvem 401 com o mesmo corpo normalizado (a2ee9af6f29f…) satisfeito
    D POST numa rota /api/v1 não é atendido; conferir qual vem primeiro, 401 ou 405 POST/PUT/PATCH/DELETE sem token devolvem 401, e não 405. O mesmo com Bearer inventado ordem observada: 401 antes de 405. Parte anônima de SC-006 (nenhuma escrita atendida) satisfeita; o código 405 não foi medido
    E /api-tokens sem sessão redireciona para a entrada e não traz conteúdo da tela 302, location: /sign-in, corpo de 74 B só com o texto do redirecionamento; 0 ocorrências de token, Copy value, tb_api_, Revoke, Generate. /sign-in responde 200 com o formulário satisfeito
    F nenhuma resposta anônima da API traz hash, prefixo ou valor de token 0 ocorrências de tb_api_, hash, token_hash, public_id, last_four, do Bearer inventado, de Elixir., Ecto, SELECT ou stacktrace nos corpos e cabeçalhos. Controle positivo: a mesma varredura acha unauthorized 5 vezes em 5 corpos satisfeito

    B. Ouvinte de the_band:copy¶

    A entrada é /sign-in (GET / responde 302 para ela). Os scripts que ela carrega:

    curl -s -o $S/signin.html "$PRODUCAO_URL/sign-in"
grep -oE '<script[^>]*src="[^"]*"' $S/signin.html
for a in app-4d7ded13443f4f88d0a881ef09d865a3 theme-f299d4c46ad2acf97d18c6bfea18f6e3; do
  curl -s -o $S/$a.js -w "$a HTTP %{http_code} %{size_download}B\n" "$PRODUCAO_URL/assets/js/$a.js?vsn=d"
  grep -o 'the_band:copy' $S/$a.js | wc -l; grep -o 'clipboard' $S/$a.js | wc -l
done
grep -o 'LiveSocket' $S/app-*.js | wc -l

    app-4d7ded13443f4f88d0a881ef09d865a3   HTTP 200 146793B   the_band:copy: 0  clipboard: 0
theme-f299d4c46ad2acf97d18c6bfea18f6e3 HTTP 200 897B      the_band:copy: 0  clipboard: 0
controle positivo (LiveSocket no app): 4

    Na v0.9.1 o botão manda o evento (lib/the_band_web/live/api_token_live/view.ex:63, JS.dispatch("the_band:copy", …)), e assets/js/app.js não tem ouvinte. Em development o ouvinte existe (assets/js/app.js:55, do #941). O que a pessoa veria em produção: na tela do token recém-gerado, clicar em "Copy value" não copia nada e não mostra erro. Isso bate com a nota (defeito herdado, corrigido e ainda não publicado). Não é regressão.

    C. API sem sessão: a recusa uniforme¶

    O formato do token vem de priv/knowledge_base/rules/api_access_thresholds.yaml na v0.9.1: tb_api_<id_publico>_<segredo>, com id de 6 bytes (8 caracteres base64url) e segredo de 32 bytes (43 caracteres). O Bearer inventado segue esse formato e tem marca de invenção: tb_api_ACEITE00_AAAA…A (59 caracteres).

    U="$PRODUCAO_URL/api/v1/teams"
curl -s -o $S/c1.b -w '%{http_code}\n' "$U"                                  # i   sem Authorization
curl -s -o $S/c2.b -w '%{http_code}\n' -H 'Authorization: Basic xyz' "$U"    # ii  malformado
curl -s -o $S/c3.b -w '%{http_code}\n' -H "Authorization: Bearer $FAKE" "$U" # iii Bearer plausível
curl -s -o $S/c4.b -w '%{http_code}\n' -H "Authorization: Bearer " "$U"      # iv  Bearer vazio
curl -s -o $S/c5.b -w '%{http_code}\n' -H "Authorization: $FAKE" "$U"        # v   token sem "Bearer"
for i in 1 2 3 4 5; do sed -E 's/"request_id":"[^"]*"/"request_id":"X"/' $S/c$i.b > $S/n$i.b; done
shasum -a 256 $S/n?.b | awk '{print $1}' | sort | uniq -c

    D. Método de escrita: a ordem entre 401 e 405¶

    for M in POST PUT PATCH DELETE; do
  curl -s -o $S/d_$M.b -w "$M HTTP %{http_code}  " -X $M "$PRODUCAO_URL/api/v1/teams"; cat $S/d_$M.b; echo
done
curl -s -o $S/d.b -w "POST com Bearer inventado HTTP %{http_code}\n" -X POST -H "Authorization: Bearer $FAKE" "$PRODUCAO_URL/api/v1/teams"
curl -s -I -w "HEAD HTTP %{http_code}\n" "$PRODUCAO_URL/api/v1/teams"

    POST   HTTP 401  {"error":{"code":"unauthorized","message":"The credential presented is not usable.","request_id":"GNhGm-LYG0E6SwEAAAWh"}}
PUT    HTTP 401  {"error":{"code":"unauthorized",…,"request_id":"GNhGm_lQ7hg6SwEAAAXB"}}
PATCH  HTTP 401  {"error":{"code":"unauthorized",…,"request_id":"GNhGnA3Ydh46SwEAAAXh"}}
DELETE HTTP 401  {"error":{"code":"unauthorized",…,"request_id":"GNhGnCJ6s0g6SwEAAAYB"}}
POST com Bearer inventado HTTP 401
HEAD   HTTP 401  (content-type: application/json)

    Ordem observada: sem credencial válida, o 401 vem antes do 405. É assim por construção: no roteador da v0.9.1, scope "/api/v1" faz pipe_through [:api, :api_autenticada], e o match :*, …, :nao_permitido só roda depois da autenticação.

    O que a spec promete: não define a precedência. O SC-006 diz "0 métodos além de GET e HEAD respondem em /api/v1". O contrato erro.md diz 405 para "qualquer método além de GET e HEAD". O quickstart §7 mede o 405 com Authorization: Bearer $TOKEN. Nenhum dos três pede 405 para quem chega sem credencial. Então a ordem observada não contradiz a spec, e o "não responde" do SC-006 se cumpre para quem chega anônimo: nenhuma escrita foi atendida. O código 405 em si só se mede com token válido.

    for pat in 'tb_api_' 'token_hash' 'hash' 'ACEITE00' 'AAAAAAAA' 'Elixir\.' 'Ecto' 'stacktrace' 'SELECT' 'last_four' 'public_id'; do
  cat $S/c?.b $S/c?.h | grep -c -- "$pat"; done

    O Bearer inventado (ACEITE00, AAAAAAAA) não é ecoado na resposta, nem no corpo nem nos cabeçalhos. A descrição OpenAPI anônima (GET /api/openapi, 200) também tem 0 ocorrências de token_hash e de um valor no formato tb_api_<id>_<segredo>.

    O que NÃO foi medido, e por quê¶

    Não medível sem conta (não há PRODUCAO_TESTE_EMAIL/PRODUCAO_TESTE_SENHA, por decisão da pessoa mantenedora em 2026-09-24):

    critério por que depende de conta
    migração do #939, vista na tela a tela que a mostra fica atrás de sessão
    as três mudanças de /api-tokens só aparecem para quem tem sessão de administração. Daqui só se vê o 302
    "Copy value" copiando de fato exige gerar um token, o que é escrita em produção. O item B mede só a ausência do ouvinte no JS. Mesmo com conta, esta medida pediria escrita. Veja o achado 3
    token válido responde 200 com dado do próprio tenant (SC-002) exige token, e criar token é escrita
    token revogado e expirado dão a mesma recusa do inexistente (SC-003, completo) exige token revogado e token expirado. Só o inexistente foi medido
    revogação corta em até a latência declarada (SC-005) exige criar e revogar
    405 method_not_allowed nos quatro métodos (SC-006, o código) o 401 vem antes sem token válido (item D)
    cabeçalhos de limite de uso só aparecem em resposta atendida. Nas respostas 401 que recebi não há cabeçalho de limite, mas isso não diz nada sobre a resposta autenticada

    De outro papel:

    critério de quem
    SC-004: o motivo real de cada recusa está no log interno, achado pelo request_id deploy-producao, que tem acesso ao log. Para isso, os request_id das recusas desta medida estão acima (por exemplo GNhGkMNIgQM6SwEAAATB = sem cabeçalho, GNhGkOek4R86SwEAAATh = Basic, GNhGl_Wj1DU6SwEAAAUh = Bearer inventado de formato válido)
    SC-001 (valor em claro em log e no banco) exige token (é escrita) e acesso a log e banco

    Achados¶

    1. Caminho inexistente sob /api/v1 responde com a página HTML do site, e não com o formato único de erro. Pode ser defeito de implementação (causa 2) ou lacuna da spec (causa 3). Quem decide é o PO. 

      curl -s -o $S/nx.b -w "HTTP %{http_code} ct=%{content_type}\n" "$PRODUCAO_URL/api/v1/nao-existe"
curl -s -o $S/nx2.b -w "HTTP %{http_code}\n" -X POST "$PRODUCAO_URL/api/v1/nao-existe"

      GET  /api/v1/nao-existe  HTTP 404 ct=text/html; charset=utf-8   <!DOCTYPE html>… <title>TheBand · The Band
POST /api/v1/nao-existe  HTTP 404                               <!DOCTYPE html>…
      FR-020 diz "um formato único para todos os códigos", e o contrato lista 404 not_found em JSON. Um cliente que escreveu "um tratador, não seis" (erro.md) recebe HTML e quebra no parse em vez de ler error.code. O que quem integra veria: um erro de JSON inválido, sem request_id, no lugar de not_found. O comentário do roteador recusa de propósito o curinga que daria 405 ("a mentira inversa"), mas nada no roteador nem nos testes de test/the_band_web/api cobre o caminho inexistente. A distinção 401/404 sem credencial não vaza nada: as 8 rotas estão publicadas na descrição OpenAPI anônima.

    2. Sem credencial, o 401 vem antes do 405 (item D). A spec não diz qual vem primeiro. O comportamento é defensável: não confirma nada a quem não se identificou. Vale deixar a ordem escrita no contrato erro.md, para que ninguém trate a ordem como defeito depois.

    3. O funcionamento do "Copy value" não se verifica em produção sem escrever lá. Para ver o botão é preciso gerar um token. Pela regra da conferência, isso é um achado sobre o critério, e não uma autorização para gerar. Mesmo com conta de teste, esse item continua de fora, a menos que se decida outra fonte de evidência (por exemplo, conferir só o JS servido, como o item B faz).

    4. (local, fora de produção) O ref main local deste checkout está parado (mix.exs 0.2.0), enquanto origin/main está em 0.9.1. Não afeta a produção. Só engana quem comparar versões contra main sem origin/.

    Classificação: nada aqui é "a release não subiu" (causa 1). A versão no ar é a esperada, e o estado do "Copy value" é o herdado e já registrado.
